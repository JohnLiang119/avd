# youtube-data-api-channel Specification

## Purpose
以使用者自填的 YouTube Data API v3 金鑰提供頻道新片擷取與批次直播狀態查詢，作為官方 RSS 與 yt-dlp 備援之前的優先通道；涵蓋金鑰的設定與機密保護、uploads 播放清單解析、每輪候選視窗上限、配額耗盡的降級與當日抑制。

## Requirements

### Requirement: API 金鑰為選填設定且未設定時行為不變

系統 MUST（必須）在頻道監控設定中提供 YouTube Data API 金鑰的輸入欄位，且該欄位 MUST（必須）為選填。未設定有效金鑰時，頻道追蹤的可觀察行為 MUST（必須）與導入本能力之前完全一致 —— 仍以官方 RSS 為第一通道、yt-dlp 備援為第二通道，且 MUST NOT（不得）因缺少金鑰而顯示錯誤、警告或功能不可用的提示。

金鑰 MUST（必須）與其他設定項一同持久化，並在應用程式重啟後正確還原。系統 MUST NOT（不得）內建、預載或以任何形式散布開發者自有的金鑰 —— 配額綁定 Google Cloud 專案而非使用者，內建單一金鑰會使所有使用者共用同一份每日配額並使該金鑰可自安裝檔取出。

#### Scenario: 未設定金鑰

- **WHEN** 使用者從未輸入 API 金鑰，或已將金鑰欄位清空
- **THEN** 系統 MUST 以官方 RSS 為第一通道執行頻道檢查
- **AND** 系統 MUST NOT 發出任何 YouTube Data API 請求
- **AND** 系統 MUST NOT 顯示要求使用者設定金鑰的錯誤或警告

#### Scenario: 設定金鑰後重啟

- **WHEN** 使用者輸入有效金鑰並儲存，隨後重新啟動應用程式
- **THEN** 系統 MUST 還原該金鑰並於後續檢查中以 API 為第一通道

#### Scenario: 金鑰僅含空白

- **WHEN** 使用者輸入的內容在去除前後空白後為空字串
- **THEN** 系統 MUST 視為未設定金鑰，MUST NOT 以空金鑰發出 API 請求

### Requirement: API 金鑰為機密，不得出現於任何可外流的輸出

API 金鑰 MUST（必須）被視為機密。系統 MUST NOT（不得）讓金鑰出現在下列任何位置：錯誤訊息、錯誤日誌、Toast 或通知文字、主控台輸出，以及頻道清單的匯出備份。

此項為**安全需求而非美化需求**：錯誤日誌設計上就是要讓使用者複製出來求助，金鑰一旦寫入其中，使用者貼出日誌時即等同公開該金鑰。凡以請求網址組成錯誤訊息的路徑，MUST（必須）在訊息中去除 query string 或以遮蔽字樣取代金鑰。

金鑰的顯示 MUST（必須）避免完整呈現；設定介面 MUST（必須）在已設定金鑰時給出可辨識的狀態指示，且 MUST NOT（不得）要求使用者為了確認狀態而讓完整金鑰可見。

#### Scenario: API 請求失敗時的錯誤訊息

- **WHEN** 帶有金鑰的 API 請求失敗（任何狀態碼或網路錯誤）
- **THEN** 產生的錯誤訊息 MUST NOT 包含金鑰的任何片段
- **AND** 該訊息寫入錯誤日誌後，日誌內容 MUST NOT 包含金鑰

#### Scenario: 匯出頻道備份

- **WHEN** 使用者匯出頻道追蹤清單備份
- **THEN** 備份內容 MUST NOT 包含 API 金鑰
- **AND** 還原該備份 MUST NOT 覆寫或清除本機已設定的金鑰

#### Scenario: 設定介面顯示已設定狀態

- **WHEN** 使用者開啟設定且金鑰已設定
- **THEN** 系統 MUST 指示金鑰已設定
- **AND** 系統 MUST NOT 預設以明文完整顯示該金鑰

### Requirement: 以 uploads 播放清單擷取頻道新片

設定有效金鑰時，系統 MUST（必須）以 YouTube Data API 擷取該頻道的上傳影片清單作為第一通道，回傳的資料 MUST（必須）轉換為與官方 RSS、yt-dlp 備援共用的內部影片結構，使上層的新片判定、關鍵字篩選與錨點計算無法察覺底層通道差異。

每支影片 MUST（必須）帶有影片識別碼、標題與**精確發布時間**。API 通道 MUST NOT（不得）以當下時間替代缺失的發布時間。

系統 MUST（必須）能由頻道識別碼取得其 uploads 播放清單識別碼。若採用識別碼前綴轉換的慣例而該清單不存在，系統 MUST（必須）改以查詢頻道詳細資料的方式取得正確的 uploads 播放清單識別碼，MUST NOT（不得）逕行判定該頻道無效。

#### Scenario: 成功以 API 取得新片

- **WHEN** 已設定有效金鑰且 API 正常回應
- **THEN** 系統 MUST 回傳該頻道最新影片清單，每支帶有影片識別碼、標題與精確發布時間
- **AND** 系統 MUST NOT 發出官方 RSS 請求，亦 MUST NOT 啟動 yt-dlp
- **AND** 回傳結果 MUST 標註來源為 API 通道

#### Scenario: uploads 播放清單以慣例推導失敗

- **WHEN** 由頻道識別碼推導出的 uploads 播放清單識別碼查詢回報不存在
- **THEN** 系統 MUST 改以查詢頻道詳細資料取得正確的 uploads 播放清單識別碼並重試
- **AND** 僅當該查詢亦確認該頻道不存在時，系統才 MUST 將其視為頻道層級的錯誤

#### Scenario: API 回傳的影片缺少發布時間

- **WHEN** API 回傳的某支影片不帶可解析的發布時間
- **THEN** 系統 MUST NOT 以當下時間替代
- **AND** 該影片 MUST 依既有「缺少精確發布時間」的錨點守門規則處理

### Requirement: API 通道每輪候選視窗上限為 50 筆

API 通道每輪 MUST（必須）最多取回 50 筆影片。此數值 MUST（必須）作為該通道的「每輪候選上限」，供既有的錨點守門規則判定 —— 當本輪取回筆數達此上限時，代表可能存在未被取回也未經比對的較舊影片，錨點的推進 MUST（必須）依既有規則受本輪最舊影片的發布時間限制。

系統 MUST NOT（不得）為了取得更多影片而對同一頻道於同一輪發出多次分頁請求 —— 那會使配額消耗隨頻道歷史長度成長，而每輪只需辨識新片。

#### Scenario: 取回筆數未達上限

- **WHEN** API 通道本輪取回的影片少於 50 筆
- **THEN** 該通道的候選視窗上限 MUST NOT 限制錨點推進

#### Scenario: 取回筆數達上限

- **WHEN** API 通道本輪取回滿 50 筆影片
- **THEN** 錨點 MUST NOT 推進至晚於本輪實際取回影片中最舊者的發布時間

#### Scenario: 不進行分頁

- **WHEN** 某頻道的上傳影片總數超過 50 筆
- **THEN** 系統 MUST 只取第一頁，MUST NOT 為該頻道於同一輪發出後續分頁請求

### Requirement: 直播狀態改以批次查詢

設定有效金鑰時，系統 MUST（必須）以單次 API 請求批次查詢多支影片的直播狀態，取代逐支影片各自發出一次查詢。單次批次請求 MUST（必須）最多涵蓋 50 支影片；候選影片超過 50 支時 MUST（必須）分批，每批仍為單一請求。

批次查詢的對象 MUST（必須）沿用既有的候選收斂規則 —— 只查詢已通過該頻道關鍵字篩選的候選影片，MUST NOT（不得）為未命中關鍵字的影片發出查詢。

#### Scenario: 候選影片少於單批上限

- **WHEN** 某輪有 8 支通過關鍵字篩選的候選影片需判定直播狀態
- **THEN** 系統 MUST 以單一 API 請求取得全部 8 支的狀態
- **AND** 系統 MUST NOT 逐支發出 8 次查詢

#### Scenario: 候選影片超過單批上限

- **WHEN** 某輪有 120 支候選影片需判定直播狀態
- **THEN** 系統 MUST 分為 3 批，每批以單一請求涵蓋最多 50 支

#### Scenario: 未命中關鍵字的影片不進入批次

- **WHEN** 某輪有影片符合既有新片條件但未命中該頻道關鍵字
- **THEN** 該影片 MUST NOT 被納入任何直播狀態批次查詢

### Requirement: 配額耗盡須降級並於當日抑制後續 API 請求

當 API 回報配額耗盡時，系統 MUST（必須）將該頻道本輪的擷取降級至官方 RSS，再依既有規則降至 yt-dlp 備援。

配額為**每日**額度，且耗盡後在配額重置前的所有後續請求必然同樣失敗。因此系統 MUST（必須）在偵測到配額耗盡後抑制當日其餘的 API 請求，MUST NOT（不得）為本輪其餘頻道或後續輪次重複嘗試 API —— 否則每個頻道每輪都要白付一次失敗請求的往返時間。抑制 MUST（必須）在配額重置後自動解除，且 MUST NOT（不得）要求使用者手動重設或重新輸入金鑰。

#### Scenario: 檢查途中配額耗盡

- **WHEN** 一輪檢查進行到第 5 個頻道時 API 回報配額耗盡
- **THEN** 該頻道 MUST 改以官方 RSS 擷取，失敗則依既有規則降至 yt-dlp 備援
- **AND** 本輪其餘頻道 MUST 直接以官方 RSS 為第一通道，MUST NOT 再發出 API 請求

#### Scenario: 配額耗盡後的後續輪次

- **WHEN** 配額已於當日耗盡，且下一輪定時檢查啟動
- **THEN** 系統 MUST 直接以官方 RSS 為第一通道，MUST NOT 再發出 API 請求

#### Scenario: 配額重置後恢復

- **WHEN** 配額重置時點已過，且新一輪檢查啟動
- **THEN** 系統 MUST 自動恢復以 API 為第一通道
- **AND** 系統 MUST NOT 要求使用者重新輸入金鑰或手動解除抑制

### Requirement: 金鑰無效須明確告知且不得靜默降級

當 API 回報金鑰無效、已撤銷或未啟用該服務時，系統 MUST（必須）明確告知使用者金鑰有問題，並降級至官方 RSS 以維持功能。

此情境 MUST NOT（不得）與配額耗盡混為一談 —— 前者需使用者修正金鑰、後者只需等待重置。系統 MUST NOT（不得）僅靜默降級而不告知，否則使用者會以為 API 通道正在生效。

系統 MUST（必須）抑制後續的 API 請求直到使用者修改金鑰，MUST NOT（不得）為每個頻道每輪重複發出必然失敗的請求。

#### Scenario: 金鑰無效

- **WHEN** API 回報金鑰無效或未啟用該服務
- **THEN** 系統 MUST 顯示可辨識為「金鑰問題」的提示，且該提示 MUST 與配額耗盡的提示不同
- **AND** 系統 MUST 降級至官方 RSS 繼續本輪檢查
- **AND** 系統 MUST 抑制後續 API 請求直到金鑰被修改

#### Scenario: 使用者修正金鑰後

- **WHEN** 使用者在金鑰無效的抑制狀態下輸入新的金鑰並儲存
- **THEN** 系統 MUST 解除抑制並於下次檢查重新嘗試 API 通道

### Requirement: 顯示當日 API 用量估算

系統 MUST（必須）在 API 金鑰的設定介面顯示當日已消耗的配額單位與每日上限。該數值 MUST（必須）明確標示為**估算值**，MUST NOT（不得）呈現為權威數字。

估算為必要的妥協：API 不提供查詢自身用量的端點，權威數字需 OAuth 授權方能取得，非 API 金鑰可得。下列情形會使估算低於實際，故不得宣稱精確：同一 Google Cloud 專案被其他工具使用、同一把金鑰用於多台裝置、以及失敗請求是否計費的不確定性。

計數 MUST（必須）在請求送達服務後累計，不論回應為成功或錯誤 —— 配額耗盡的回應本身也消耗配額。傳輸層錯誤（請求未送達服務）MUST NOT（不得）計入。

計數 MUST（必須）於每日配額重置時點（太平洋時間午夜）歸零，且該歸零 MUST（必須）與配額耗盡抑制採用同一時點計算，兩者 MUST NOT（不得）各自為政。計數 MUST（必須）持久化，重啟後不歸零。

未設定金鑰時 MUST NOT（不得）顯示用量。每分鐘配額 MUST NOT（不得）呈現 —— 其為專案層級數百萬單位，與本能力的用量相差數個數量級，顯示徒增雜訊。

#### Scenario: 成功的請求計入用量

- **WHEN** 系統成功完成一次 API 請求
- **THEN** 當日用量估算 MUST 增加該請求的配額成本

#### Scenario: 服務回報錯誤的請求仍計入用量

- **WHEN** API 以配額耗盡或金鑰無效等錯誤回應一次請求
- **THEN** 當日用量估算 MUST 仍增加該請求的配額成本 —— 該請求確實被服務處理過

#### Scenario: 傳輸層錯誤不計入用量

- **WHEN** 一次 API 請求因網路不可達而未送達服務
- **THEN** 當日用量估算 MUST NOT 增加

#### Scenario: 每日重置時歸零

- **WHEN** 系統於配額重置時點之後首次累計用量
- **THEN** 當日用量估算 MUST 自零重新起算
- **AND** 該時點 MUST 與配額耗盡抑制的解除時點以同一方式計算

#### Scenario: 重啟後保留當日累計

- **WHEN** 使用者於同一配額日內重新啟動應用程式
- **THEN** 當日用量估算 MUST 保留重啟前的累計值，MUST NOT 歸零

#### Scenario: 未設定金鑰時不顯示用量

- **WHEN** 使用者未設定 API 金鑰
- **THEN** 系統 MUST NOT 顯示當日用量估算
