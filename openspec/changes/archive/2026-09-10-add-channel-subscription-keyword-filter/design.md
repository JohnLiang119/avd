## Context

參見 `proposal.md` 的動機。頻道訂閱目前以 `MonitoredChannel[]` 儲存在 `avd_monitored_channels`，自動與手動檢查會先取得完整 RSS／備援影片陣列，再透過既有新片判定、直播狀態檢查與時間錨點建立下載任務。頻道備份直接序列化同一份訂閱資料，覆蓋與合併還原則各自重建頻道物件。

本變更跨越訂閱 UI、持久化正規化、檢查流程、模擬流程及備份還原，因此需要共用比對邏輯與明確的錨點順序。完整行為契約見 `specs/channel-auto-monitor/spec.md` 與 `specs/channel-backup-restore/spec.md`。

## Goals / Non-Goals

**Goals:**

- 以單一共用規則正規化關鍵字並比對影片標題。
- 讓既有訂閱與舊版備份在未提供新欄位時自動採用空清單。
- 在不增加 RSS／備援請求次數的前提下，阻止未命中影片建立下載任務。
- 保持既有首次訂閱、去重、直播保留與時間錨點安全規則。
- 讓頻道卡片可管理多個關鍵字，同時維持現有雙行響應式版面。

**Non-Goals:**

- 不比對影片說明、標籤、頻道名稱或字幕。
- 不支援 AND、排除字、規則運算式或模糊搜尋語法。
- 不回溯掃描或下載修改關鍵字前已檢查的影片。
- 不改變 RSS／yt-dlp 備援、錯誤分類、熔斷門檻或外部請求協定。

## Decisions

下列決策標題中的【D-x】為 `tasks.md` 使用的交叉引用代號；`tasks.md` 中標註【D-x】的任務即以對應決策為依據。

### 1.【D-I】在訂閱物件保存選填的字串陣列

**Decision:** 在頻道訂閱資料加入 `keywords?: string[]`。頻道物件實際有**三個**建構點——頻道管理彈窗新增、主畫面網址列自動加入追蹤、備份還原匯入（覆蓋與合併）——加上持久化反序列化，共四處皆透過同一正規化函式產生 `string[]`；缺少欄位或內容無效時得到空陣列。實作時須以搜尋建構點的方式確認沒有遺漏（網址列那條路徑的欄位集合與彈窗不同，容易被漏掉）。

**Rationale:** 現有儲存與備份均直接序列化頻道物件，選填欄位可在不建立資料庫遷移或新儲存鍵的情況下向下相容。明確寫回空陣列也能讓後續 UI 與檢查程式不必反覆處理 `undefined`。

**Alternatives:** 以逗號分隔字串保存較難正確處理空白、重複值與未來格式演進；另建全域關鍵字表則無法表達每個頻道不同的主題需求。

### 2.【D-D】【D-E：空白判定】使用共用純函式定義正規化與 OR 比對

**Decision:** 在既有的 `src/composables/useChannelMatching.ts`（已放置 `selectNewVideos`、`nextChannelBaseline` 等純函式與其測試）提供可測試的純函式：

- 將輸入限制為字串、去除前後空白並移除空項；「空白」的判定 MUST 涵蓋 Unicode 空白與零寬字元（U+200B～U+200D、U+2060、U+FEFF）——JavaScript 的 `trim()` 不會移除零寬空格，若不處理會產生一個永不命中的關鍵字。
- 以正規化值去除重複項目，但保留使用者輸入的第一個對應項目之**原始大小寫**作為顯示文字。
- 空清單一律回傳符合；非空清單則對正規化後的影片標題執行 `some` 子字串比對。

自動排程、立即檢查、單一頻道模擬、全部頻道模擬及備份還原 MUST 共用這些函式，不在各呼叫點重寫比對規則。

**Rationale:** 純函式可直接覆蓋中文、英文大小寫、空白、重複及無效輸入測試，並避免不同入口產生行為漂移。選既有的 `useChannelMatching.ts` 而非新開模組，是因為關鍵字命中本質上就是新片判定的第三個條件，與該檔既有的錨點／去重邏輯同屬一組概念。

**Alternatives:** 直接在 `App.vue` 各迴圈內呼叫 `includes` 較少程式碼，但會複製正規化規則且難以完整測試——`checkAllMonitoredChannels` 等函式是 `<script setup>` 內未匯出的內嵌函式，專案也未安裝 `@vue/test-utils`，寫在那裡的邏輯無法自動測試。

### 2b.【D-A】字形正規化：全形折半形 + 中文字形折算到同一域，再忽略英文大小寫

**Decision:** 關鍵字與影片標題在比對前 MUST 各自經過同一組正規化：先 NFKC（全形英數→半形）、再以既有的 `opencc-js` 把兩側折算到同一中文字形域（簡體）、最後轉小寫。

**Rationale:** 這是本設計最容易被忽略卻一定會踩到的一點。影片標題在入庫前已被 `convertCnToTw` 改寫，而該轉換是**整串**啟發式——標題只要含任一繁體專屬字就整串保持原狀，否則整串簡轉繁。以專案自帶的 opencc-js 實測：

```
"机器学习入门"  →  "機器學習入門"     （全簡體，整串轉繁）
"機器学习入門"  →  "機器学习入門"     （只因含「機」一字，其餘保持簡體）
```

也就是說**同一個詞在不同標題中會以不同字形入庫**。若直接比對，使用者設「學習」時第一支命中、第二支漏抓；設「学习」則完全相反，而使用者無從理解為何同系列影片時而命中。兩側折算到同一字形域是唯一能讓結果穩定的做法。

全形英數同理：`'ＡＩ'.toLowerCase()` 得到 `'ａｉ'`，不會命中 `'ai'`；本專案目前沒有任何 `normalize()` 呼叫。

**Non-Goals（明確不處理，避免實作者自行加碼）：** 日文假名互轉（平假名／片假名）、emoji 正規化、異體字對映。

**Alternatives:** 只在儲存關鍵字時做一次轉換，但標題字形不穩定的問題出在標題側，單邊處理無效；改為保留 YouTube 原標題另存一份供比對，則牽動任務標題與去重的既有契約，改動面過大。

### 3.【D-C】先判定新片，再於本機過濾，錨點仍以完整 Feed 計算

**Decision:** 每個頻道只取得一次影片陣列。首次追蹤仍以完整陣列的最新影片建立錨點；後續檢查先沿用既有新片與佇列去重判定，再只對命中關鍵字的候選影片執行直播狀態檢查與建立任務。完成後仍把完整影片陣列交給既有錨點計算，只有「已命中但因直播或狀態未知而未處理」的影片加入既有未處理集合——但錨點的實際推進另受決策 3b、3c 的上限守門約束（未命中影片可被越過，未處理影片與未取回的較舊影片則不可）。

**Rationale:** 未命中影片是使用者明確要求永久略過的項目，錨點應越過它們，否則每次輪詢都會重新比對。直播或狀態未知影片則仍可能在之後變成可下載內容，必須保持現有不越過規則。先做關鍵字過濾也可避免對確定不要的影片提出直播狀態查詢。

**Alternatives:** 以過濾後陣列計算錨點會讓未命中影片反覆出現；在 RSS URL 加入關鍵字不可行，且會破壞一次擷取的限制。

### 3b.【D-B】【必要的前置修正】錨點守門改為「不得超過任何未處理影片」

**Decision:** 修正 `nextChannelBaseline` 的守門條件：錨點 MUST NOT 超過任何未處理影片的發布時間（以未處理影片的**最小**發布時間為上限），而非現行的「把未處理影片從候選中剔除後取最大值」。

**Rationale:** 現行實作只是把未處理影片排除在候選之外，再取剩餘影片的最大發布時間。在本 change 之前這通常無害，因為未處理影片往往就是最新的那一支；但一旦引入關鍵字篩選，「較新的未命中影片」會大量出現，於是：

```
Feed:  [新] 未命中影片（可被越過）   ← 錨點推到這裡
       [舊] 命中但為直播的影片        ← 被連帶越過，日後轉存檔也不再被視為新片
```

決策 3 聲稱「保持現有不越過規則」，但在新的資料形狀下該規則會被靜默抵銷，直播守門實質失效。既有測試只覆蓋「未處理影片恰為最新」的情形，抓不到這個組合，因此必須連同新測試一起修。

**Alternatives:** 把未命中影片也加入未處理集合可避免此問題，但那會讓錨點永遠停在最舊的未命中影片、每輪重複比對整個 Feed，違背決策 3 的目的。

### 3c.【D-F】候選視窗差異須可觀測

**Decision:** 官方 RSS 每輪回傳約 15 筆，yt-dlp 備援每輪只取 2 筆。當本輪以備援取得且筆數達上限時，系統 MUST NOT 將錨點推進至超過本輪實際取回的最舊影片之前。

**Rationale:** 決策 2 保證兩種來源使用相同的比對規則，但真正決定命中率的是**候選視窗大小**。備援只有 2 筆時，錨點若直接推到這 2 筆中的最新者，會跨過所有未被取回的影片——沒有關鍵字時這只是漏抓，有關鍵字時使用者更難察覺（會誤以為是「沒有命中」）。

**Alternatives:** 提高備援上限會拉長 yt-dlp 執行時間且改動既有擷取契約，不在本 change 範圍。

### 4. 模擬入口選取最新的命中影片

**Decision:** 單頻道模擬從完整結果中選擇第一支命中影片；全頻道模擬則先篩選，再對每個頻道取最新兩支命中影片。無命中時不建立任務並顯示專用提示。

**Rationale:** 模擬功能仍會實際建立下載任務，若繞過關鍵字會使使用者誤認正式排程也不受篩選控制。

**Alternatives:** 讓模擬永遠下載最新影片雖可測試連線，卻違反「有關鍵字只抓命中影片」的可觀察行為。

### 5.【D-E：輸入上限與逗號】以卡片入口開啟暫存式關鍵字編輯器

**Decision:** 在既有頻道卡片第二行加入精簡的關鍵字入口，顯示「全部影片」或關鍵字數量；點擊後開啟獨立對話框，以標籤方式新增、刪除與清空關鍵字。輸入支援 Enter、半形逗號及全形逗號分隔。編輯內容先存於草稿，只有確認儲存時才提交；取消不改變訂閱。

輸入契約：每頻道關鍵字數上限 20、單項長度上限 100 字元，超限 MUST 拒絕並提示、不得靜默截斷；逗號既為分隔符，MUST 明確告知逗號不可作為關鍵字內容。

**Rationale:** 獨立對話框可避免在手機寬度中塞入長關鍵字，也不需要把既有雙行頻道卡片擴成第三行。草稿式編輯讓「取消」有明確語意——這是選擇提交時整份替換的真正理由。

**注意（前一版的錯誤前提已修正）：** 先前版本以「巢狀陣列原地修改不會觸發持久化，所以必須替換物件」為理由，該前提**不成立**——`useStorage` 的 watch 已是 `{ deep: true }`，原地 `keywords.push()` 一樣會持久化。因此「替換物件」純屬草稿／確認語意與不可變資料風格的選擇，不是持久化的必要條件；實作時不需為此增加額外複雜度。

**Alternatives:** 卡片內直接放逗號字串輸入框會破壞響應式版面且缺乏清楚的多項操作；新增第三行則與現有雙行卡片規格衝突（該版面是 `channel-ui-layout` 的明文需求，本 change 已將其列為 Modified Capability）。

### 5b.【D-G】檢查結果提示須區分「沒有新影片」與「全部被篩除」

**Decision:** 「本輪有 N 部符合既有新片條件的影片、但全部未命中關鍵字」MUST 與「目前沒有新影片」顯示不同訊息；「發現 N 部新影片」的 N MUST 只計入實際建立下載任務的影片數。所有屬於檢查結果提示的需求集中寫在 `channel-check-feedback` 的 delta，不在 `channel-auto-monitor` 重複規定同一則字串。

**Rationale:** `channel-check-feedback` 這個能力的 Purpose 逐字寫著「避免假陽性的『沒有新影片』誤導」，而現行程式的分支條件只看 `newVideoCount`——加入關鍵字後，「抓到 12 支新片但全部不命中」會走進「目前沒有新影片」，正好製造該能力當初要修掉的那種誤導訊息。

### 6.【D-H】備份格式沿用頻道物件並在還原邊界正規化

**Decision:** 匯出前確保記憶體中的關鍵字已正規化，因此現有 JSON 匯出流程（Android 端透過系統分享面板可分享至雲端硬碟；程式碼本身沒有獨立的雲端備份路徑）可自然攜帶欄位。覆蓋與合併新增頻道時顯式正規化匯入值；合併遇到重複 Channel ID 時維持現況，不覆寫本機頻道或關鍵字，但 MUST 告知有幾個頻道的匯入關鍵字未被套用。

覆蓋還原另有一項安全規則：若備份中某頻道的錨點**晚於**本機現值，MUST 保留較舊（較保守）者。

**Rationale:** 不需新增備份版本協定，舊版程式會忽略未知欄位，現行程式也能把缺少欄位的舊備份解讀為空清單。

錨點取較保守值的理由是關鍵字改變了錨點的語意：本 change 之後，錨點推進不再只代表「已下載」，也代表「已略過（未命中）」。A 裝置設了關鍵字、快速把錨點推到最新，備份還原到未設關鍵字的 B 裝置時，若直接採用較新的錨點，B 裝置會永久漏掉那批影片——而使用者的預期恰好相反（B 沒設關鍵字，應該全都要）。合併時保留本機設定卻不告知，也會讓使用者以為關鍵字已同步。

**Alternatives:** 提升獨立備份 schema 版本並增加轉換器，對單一選填欄位而言複雜度過高。

## Risks / Trade-offs

- **[影片標題日後改成命中關鍵字仍不會回補]** → 規格明確採未來式篩選；若日後需要回補，另行設計手動歷史掃描功能。
- **[使用者誤以為關鍵字能降低頻道 Feed 請求]** → UI 文案標示為「影片標題篩選」，並維持每頻道一次擷取的測試。
- **[錨點語意變更：推進不再只代表「已下載」，也代表「已略過」]** → 這是本 change 影響最深遠的一點。連帶影響兩處：錨點守門必須改為不得越過任何未處理影片（決策 3b），跨裝置覆蓋還原必須取較保守的錨點（決策 6）。
- **[簡繁轉換使入庫標題字形不穩定]** → 兩側折算到同一字形域（決策 2b），並以混合字形的固定案例測試釘住行為。
- **[備援資料標題格式與 RSS 不同、候選視窗也不同]** → 在來源轉成共用影片模型後才比對；候選視窗差異另以決策 3c 處理，不只靠「比對規則相同」的保證。
- **[關鍵字入口壓縮手機卡片空間]** → 僅顯示狀態與數量，完整內容留在對話框，並執行響應式 UI 驗證。
- **[本 change 與 `fix-live-stream-handling` 修改同一條 `auto-check-filtering` 需求]** → 見 proposal.md「與其他 change 的依賴」；歸檔前須確認 delta 基底文字與當時的主規格一致。
- **[大量行為位於 `App.vue` 的內嵌函式，無法自動測試]** → 純判定邏輯抽進 `useChannelMatching.ts` 以單元測試覆蓋，實際佈線行為誠實列為人工驗證，不在 tasks 中宣稱有自動測試。

## Migration Plan

1. 先加入純函式與單元測試，再擴充訂閱反序列化，使所有既有資料得到空關鍵字清單。
2. 接入自動、手動與模擬檢查，確認完整 Feed 仍負責錨點更新。
3. 加入頻道關鍵字編輯 UI 與備份還原正規化。
4. 執行前端型別檢查、單元測試、桌面建置與 Android 編譯驗證。
5. 若需回滾，舊版可忽略儲存與備份 JSON 中新增的 `keywords` 欄位，不需資料降級處理。
