## Context

動機與盤點數據見 `proposal.md` 的 Why。行為契約見三份 delta spec。

本 change 的形狀與前兩個完全不同：前兩個的風險在邏輯，可用單元測試收斂；本 change 有九成的改動面是**呈現層**，而呈現層在本專案沒有任何自動測試（`App.vue` 四千餘行，未安裝 `@vue/test-utils`）。設計因此聚焦在兩件事：**哪些東西不能被簡化掉**，以及**怎麼讓人工驗證可切塊進行**。

既有樣式全部是行內 `style`，沒有 CSS 框架也沒有設計代幣。這既是限制也是機會 —— 沒有樣式表要重構，但也沒有集中的地方可以一次改掉所有顏色。

## Goals / Non-Goals

**Goals:**

- 極簡化之後，每一個操作仍可被看見、被辨識、被區分、被點到。
- 不可逆的操作在觸控裝置上可與可復原者區別（現況只靠 hover 提示，在手機上等於沒有）。
- 頻道頭像能自我修復，不需使用者重新加入頻道。
- 人工驗證可逐畫面進行，不必整包改完才知道哪裡破。

**Non-Goals:**

- 不改任何功能行為。
- 不引入 CSS 框架、設計系統套件或樣式抽象層。
- 不重構 `App.vue` 的結構。本 change 只改樣式與標示，不動邏輯或元件切分。

## Decisions

### 1.【D-A】顏色的規則收斂成一句話，而不是一張色票表

**Decision:** 規格只寫「不可逆或會遺失設定的操作 MUST 與可復原者可區別」與「強調色只用於此類操作」，**不寫任何色碼**。實際的中性色階與紅色色值屬實作，寫在程式碼裡。

**Rationale:** 規格描述的是行為契約 —— 使用者能不能分辨。把 `#dc2626` 寫進規格會把一個實作細節鎖成契約，日後調整色調就得改規格；而真正該被保護的「兩者必須可分辨」反而被色碼綁架成「必須是這個紅」。

更重要的是這條規則同時是**安全**規則。現況四處有兩顆緊鄰的刪除鈕（可復原／不可逆）共用同一個圖示，只靠顏色與 `title` 提示區分，而觸控裝置沒有 hover —— 在手機上唯一的區辨就是顏色。收斂調色盤若不同時收斂顏色的**用途**，就會把這個唯一的區辨也拿掉。

**反直覺之處值得記下：** 抽掉藍、綠、橘、琥珀之後，剩下的紅色會比現在**更**顯眼。四種裝飾色同時存在時，紅色只是五分之一；成為唯一的顏色之後，它才真正是警告。極簡在此同時是視覺簡化與安全改善，兩者不衝突。

**Alternatives:** 全灰階、不可逆操作加文字標籤 —— 更安全，但會破壞佇列列的按鈕節奏且使該列變寬。使用者已明確選擇「只靠紅色」。

### 2.【D-B】單一字元的選用以「動作的形狀」為準，並全 app 一致

**Decision:**

```
  動作                          字元   出現次數
  --------------------------   ----   --------
  playVideo                      ▸        4
  uploadToDrive                  ↑        2
  removeTask / removeSubTask     ×        6
  deleteDownloadedFile           ×        4   （紅色，唯一的顏色）
  表單送出（連結 Drive）          ↓        1
  removeMonitoredChannel        （不改，維持既有外觀）      1
```

同一動作在全應用程式使用同一個字元，不同動作 MUST NOT 共用同一個字元而無其他區辨。

**Rationale:** `×` 由 `removeTask` 與 `deleteDownloadedFile` 共用是唯一的例外，而它們正是相鄰的那一對 —— 這是刻意的：兩者的**動作類別相同**（都是刪除），差別在**後果是否可逆**，而後果的差異由顏色承載。用兩個不同字元反而會暗示這是兩種不同的操作，模糊了「同樣是刪，一個可救一個不可救」這個真正重要的區別。

**Alternatives:** 為不可逆者另選字元 —— 找不到既不是 emoji、又能表達「永久」的字元；勉強挑一個只會製造新的猜謎。

### 3.【D-C】`removeMonitoredChannel` 的例外寫進規格，而非留作實作的漏網

**Decision:** 取消追蹤按鈕維持既有外觀，且此例外**明文寫入 `channel-ui-layout`**，連同理由。

**Rationale:** 一個「看起來沒改到」的按鈕，若只存在於實作而不在規格中，日後任何人做視覺一致性的清理都會順手把它改掉 —— 而理由（緊鄰開關、無二次確認、關鍵字設定會永久遺失）不會跟著留下來。寫進規格使它成為一個有理由的決定，而不是一個遺漏。

它保留紅色也符合【D-A】的規則：移除頻道雖可重新加入，但該頻道的關鍵字設定永久消失，屬「會遺失設定」。

### 4.【D-D】頭像與名稱共用同一個請求，且修復條件以「缺什麼補什麼」為準

**Decision:** 頭像自既有的 `channels.list?part=snippet` 請求一併取得（擴充欄位遮罩），不另發請求。修復的觸發條件由「名稱看似識別碼」改為「名稱看似識別碼**或**頭像缺失」。

**Rationale:** 兩者本就來自同一個資源，分開請求等於為同一份資料付兩次配額。而觸發條件是這個修復真正的關鍵 —— 使用者目前的頻道正是「名稱正常、頭像缺失」，舊條件對它們永遠不會成立。把條件改成逐項檢查「這個欄位缺了嗎」，而非用名稱當作整體健康度的代理指標。

**此擴充會觸動 `speed-up-channel-check` 建立的遮罩一致性測試** —— 該測試對遮罩的葉路徑集合有明確斷言，加欄位必須同步更新測試。那是刻意的設計：它強迫欄位的增減是深思過的，而非順手。

### 5.【D-E】載入失敗改為清空而非替換，使失效狀態可被察覺

**Decision:** 頭像 `<img>` 載入失敗時清空已儲存的網址（使其進入「缺失」狀態並於下輪修復重抓），取代目前直接換成 YouTube favicon 的作法。

**Rationale:** 現況的錯誤處理是**把壞掉的狀態藏起來**：換上 favicon 之後畫面看起來沒事，但該頻道永遠不會恢復成正確的頭像，而且沒有任何跡象顯示出過問題。YouTube 的頭像網址會過期輪替，所以這不是罕見情形。改為清空之後，失敗變成一個「待修復」的狀態，而修復機制已經存在。

### 6.【D-F】按畫面切任務，而非按檔案或按改動類型切

**Decision:** 實作任務以**畫面**為單位分組（主佇列、頻道管理彈窗、設定、各對話框、TV 模式），每一組各自附帶該畫面的人工驗證。

**Rationale:** 若按改動類型切（先刪所有 emoji、再改所有按鈕、再收斂調色盤），任何一項都會橫跨整個 app，使用者要等三輪都做完才看得到任何一個畫面的完整結果，而版面破裂會混在一起難以歸因。按畫面切則每完成一組就有一塊可驗收的成果，破了也知道是剛剛那組造成的。

代價是同一類改動會分散在多個任務中，一致性要靠【D-B】的字元對照表與【D-A】的顏色規則維持，而非靠「一次全改完」。這個代價是值得的 —— 一致性可以用規則保證，可歸因性不行。

## Risks / Trade-offs

- **[版面破裂且沒有自動測試可攔]** → 本 change 的主要風險。以【D-F】按畫面切任務加逐畫面人工驗證收斂；每一組改動都小到可單獨回退。
- **[相鄰的兩顆 × 在收斂調色盤後變得無法區分]** → 最危險的單一情形，因為其中一顆不可逆且二次確認可被使用者關閉。以【D-A】把顏色規則寫成規格、並於人工驗證中明列此項為必驗。
- **[拿掉外框使按鈕變得難以點中]** → `visual-language` 明訂視覺尺寸與觸控範圍須分開處理。實作上以 padding 維持可點區域，視覺上只留文字。
- **[頭像欄位遮罩改錯導致頭像靜默消失]** → 由 `speed-up-channel-check` 既有的遮罩一致性測試攔截，該測試對葉路徑集合有斷言。
- **[訊息 emoji 拿掉後使用者分不出成功與失敗]** → 規格要求嚴重程度改由措辭承載。實作時須確認失敗訊息的措辭本身已足夠明確，而非倚賴先前的 ❌ 傳達。

## Migration Plan

1. 先做頻道頭像（有自動測試、成果立即可見，且與其餘改動獨立）。
2. 建立字元對照表與顏色規則於實作中的單一來源，供後續各畫面引用。
3. 逐畫面進行：頻道管理彈窗（使用者的起點）→ 主佇列（密度最高、風險最大）→ 設定與各對話框 → TV 模式。
4. 每組完成後跑建置驗證，並由使用者驗收該畫面。
5. 全數完成後進版。

**回滾**：無資料模型變更，亦無行為變更。頭像的欄位擴充於回滾後僅是少取一個欄位。各畫面的視覺改動彼此獨立，可單獨回退某一畫面而不影響其他。

## Open Questions

- **中性佔位的具體形狀**（頻道頭像尚未取得時）：一個灰色圓形、頻道名稱首字、或空白圓框。三者都符合規格的「不帶品牌意涵」，差異純屬美感，且可於實作時看到實際效果再定。不影響規格、approach 或任務拆解。
