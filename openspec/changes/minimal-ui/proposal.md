## Why

使用者要求介面走極簡風：**整個 app 的圖像一律拿掉，只保留頻道頭像**。

而頻道頭像目前是壞的 —— 頻道卡片上顯示的是 YouTube 標誌，不是該頻道的頭像。盤點後這不是「圖沒載入」，是**頭像從一開始就沒被存進去**：

```
  使用者輸入              thumbnail 的結果
  ---------------------   -----------------------------
  UC 開頭的頻道 ID        ""  <- 寫死的空字串
  .../channel/UC...       ""  <- 寫死的空字串
  @handle 或一般網址      試著自 og:image 抓（可能失敗）
  yt-dlp 後備路徑         從頭到尾沒設過這個欄位
```

且**頭像只在加入頻道那一刻抓一次，之後永不更新**。既有的啟動修復只處理「標題長得像頻道 ID」的情形，所以標題正常、頭像空白的頻道（使用者目前兩個都是）**永遠不會被修復**。`<img>` 的錯誤處理又直接換成 YouTube favicon，把壞掉的狀態藏了起來。

修法幾乎免費：`channels.list?part=snippet` 的回應本就含頻道頭像，而系統**已經在打這個請求**（取得頻道名稱用）。加一個欄位即可，零額外配額。

極簡化本身的盤點結果：

```
  層次                      數量    拿掉的後果
  ----------------------  ------  --------------------------------
  <img> 標籤                 1     就是頻道頭像，唯一要保留的
  裝飾性 emoji              54     純減法，沒有損失
  有文字的按鈕圖示          ~16     沒有損失（文字還在）
  純圖示按鈕                18     變成看不見的空白按鈕
  執行期訊息 emoji          14     Toast 失去視覺分級
```

盤點中另發現一處**既有的安全問題**：四個位置有兩顆緊鄰的刪除按鈕（「清除卡片紀錄」可復原、「徹底刪除實體檔案」不可逆），兩者使用**同一個圖示**，目前只靠兩件事區分 —— 顏色，以及 `title` 提示文字。而**觸控裝置沒有 hover，`title` 永遠不會顯示**。也就是說在手機上，可復原與不可逆的刪除只差一個顏色。若極簡化把調色盤一併收斂成純灰階，這個唯一的區辨就消失了。

## What Changes

- **BREAKING（視覺）：移除全 app 的裝飾性圖像。** 54 處 emoji、約 16 個有文字按鈕的圖示、14 處執行期訊息 emoji 一律拿掉。
- **18 顆純圖示按鈕改為單一字元**：`▸`（播放）、`↑`（上傳）、`×`（移除）、`↓`（送出）。
- **調色盤收斂為「灰階 + 單一紅色」**，且紅色的用途收斂為一條規則：**只用於不可逆或會遺失設定的操作**。其餘藍／綠／橘／琥珀的裝飾性用色全部拿掉 —— 抽掉之後，那唯一的紅色反而比現在顯眼得多，所以這同時是安全的改善而非退讓。
- **容器層級拆解**：頻道卡片目前是盒中盒（白卡內還有灰底盒），改為以髮絲分隔線與留白分組。
- **頻道卡片由雙行改為三行**，使最新影片標題有呼吸空間（現況第二行已過載，標題被截到只剩數字）。
- **頻道頭像改以 API 取得並可自我修復**：修復觸發條件由「標題像頻道 ID」放寬為「標題像頻道 ID **或** 頭像缺失」；圖片載入失敗時清空已存網址以便下輪重抓，取代目前直接換成 YouTube favicon 的作法。

**刻意的例外：`removeMonitoredChannel`（頻道卡片右上角）維持現有外觀**，不納入單一字元改造。它緊鄰啟用開關且沒有二次確認，縮小視覺目標會提高誤觸機率。它保留紅色也符合上述規則 —— 移除頻道雖可重新加入，但該頻道的關鍵字設定會永久消失。

**Non-goals：**

- 不改動任何功能行為。本 change 只動呈現層與頻道頭像的取得，不動下載、解析、追蹤判定。
- 不為 `removeMonitoredChannel` 新增二次確認（使用者明確選擇維持現狀）。
- 不引入 CSS 框架或設計系統套件。既有樣式是行內 style，維持之。

## Capabilities

### New Capabilities

- `visual-language`: 全 app 的視覺契約 —— 介面不得以裝飾性圖像傳達資訊、操作控制項須可辨識且不得僅倚賴 hover 提示、顏色須承載語意、視覺簡化不得縮小觸控範圍。

### Modified Capabilities

- `channel-ui-layout`: 卡片結構由雙行改為三行；頭像 MUST 為該頻道的真實頭像而非通用標誌。
- `youtube-data-api-channel`: 新增「以 API 取得並修復頻道頭像」。

## Impact

- `src/App.vue`：54 處 emoji、約 34 個 `icon=` 屬性、18 顆純圖示按鈕、調色盤、容器層級。**這是本 change 絕大部分的改動面**，分佈於 43 行。
- `src/services/youtubeDataApi.ts`：`CHANNEL_SNIPPET_FIELDS` 擴充以納入頭像欄位，並新增其解析。昨日 `speed-up-channel-check` 建立的遮罩一致性測試會強制此擴充是刻意的 —— 遮罩的葉路徑集合有斷言，加欄位必須同步改測試。
- `src/services/DownloadService.ts`：`fetchChannelTitle` 改為同時回傳頭像（或新增對應函式）。
- `android/.../YoutubeDlPlugin.java`：`resolveChannel` 兩處寫死的空字串 —— 可留待 API 修復承接，不一定要動 Java。實作時判斷。
- 測試：頭像解析與修復觸發條件為純函式，可測；**視覺改動無自動測試覆蓋**，見下。

## 風險的正面聲明：這個 change 的風險在視覺回歸，而視覺回歸沒有自動測試

前兩個 change 的風險在邏輯，可用單元測試收斂。本 change 不同：

```
  改動面                          自動測試抓得到嗎
  ----------------------------  ------------------
  54 處 emoji + 34 個 icon           x
  18 顆按鈕改字元                     x
  調色盤收斂                          x
  容器層級拆解（版面可能破）            x
  頻道頭像（API + 修復觸發）           v  純函式可測
```

`App.vue` 超過四千行且本專案未安裝 `@vue/test-utils`，沒有元件測試。因此任務**按畫面切而非按檔案切**，每個畫面各自有一項人工驗證：主佇列、頻道管理彈窗、設定、各對話框、TV 模式。使用者可逐塊驗收，不必整包改完才知道哪裡破。

## 與其他 change 的依賴

`api-only-channel-tracking`（30/34）與 `speed-up-channel-check`（23/31）皆已實作並發布，但**尚未歸檔**（兩者的人工驗證未完成）。

本 change 對 `youtube-data-api-channel` 採 **ADDED** 而非 MODIFIED，刻意不去改 `api-only-channel-tracking` 新增的「以 API 取得頻道名稱」—— 那條 Requirement 尚未進入主規格，MODIFY 它會產生歸檔順序的相依。採 ADDED 則三者互不覆寫，歸檔順序不受限制。
