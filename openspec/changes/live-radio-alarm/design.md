## Context

動機見 proposal.md「Why」。本節只記與做法直接相關的現況與限制。

- **播放路徑只有一條**：`DownloadService.playVideo` 在 Android 以 `ACTION_VIEW` 交給外部播放器、在 Windows 以 `open` 交給系統，App 內沒有播放器，也沒有任何背景執行的機制可在 WebView 停擺時動作。
- **既有的「定時」都是 JS 計時器**：頻道追蹤以 `setInterval` 輪詢，只在 App 活著時有效，不能當鬧鐘用。
- **Android 端已有前景服務基礎**：`KeepAliveService`（`dataSync` 型、notification id 1、channel `DownloadChannel`），持有 WakeLock 與 WifiLock 供下載使用。鬧鐘播放不能共用它 —— 型別不同（需 `mediaPlayback`），生命週期也不同（下載結束會 `stopSelf`）。
- **設定持久化在 Android 是 WebView 的 localStorage**（`LocalStorageAdapter`），原生端讀不到；`config-persistence` 規格要求所有設定走這個單一介面。本 change 以 MODIFIED delta 補上「原生端權威」例外，見 specs。
- **App 為側載發行**（GitHub Releases），不受 Google Play 對鬧鐘權限的政策限制，可以宣告 `USE_EXACT_ALARM`。
- **直播來源已實測**：官方播放頁以 jQuery 呼叫 `https://www.bcc.com.tw/webapi/BCCRadioWebAPI/ChannelInfoBat`，回傳各頻道的 `androidStream`（http）與 `iosStream`（https）；中廣新聞網目前為 `https://stream.rcs.revma.com/fgtx07f3qtzuv`，無長度的 ADTS AAC 串流，`curl` 可直接讀到音訊資料。社群資料庫（radio-browser）記載的是另一個 key，說明 **串流 key 會變**，不能只寫死。
- **節目時間**：06:00《早安新聞》／《中廣 10 分鐘早報》、07:00《中廣早報新聞》／《葉蓉早報》（維基百科與官方節目表，名稱不一，時段一致）。
- **minSdk 24、targetSdk 36**；`build.gradle` 已有 `google()` 與 `mavenCentral()`，加 media3 不需新增倉庫。JUnit 4 已在 `testImplementation`。

## Goals / Non-Goals

**Goals:**

- 時間到就響，可靠度對齊系統鬧鐘：Doze、螢幕關閉、App 被系統回收、重開機後皆成立。
- 串流網址變動時不需發新版：先問官方、再退回上次成功、最後退回內建。
- 所有新增的原生狀態（設定、上次結果、快取網址）集中一處，前端不另存。
- 不動既有的下載、頻道追蹤、`KeepAliveService`。

**Non-Goals:**

- Windows/Tauri 與 Android TV 的定時播放。
- 星期篩選、假日略過、多電台清單（中廣其他四個頻道雖可自同一 API 取得，不在本次）。
- App 內的一般播放器（下載檔仍交外部播放器）。
- 錄音、節目表顯示、「現正播出」資訊（API 有 `program` 欄位，留待日後）。
- 自 AVD 任務卡片直接「設為鬧鐘」—— 本地檔案頻道的第二個入口，底層可走同一個複製流程（見 D15）。

## Decisions

### D1 排程用 `AlarmManager.setAlarmClock()`，一律登錄「下一次」單次觸發

- **選擇**：每筆啟用時間各登錄一個 `setAlarmClock()`，觸發後在接收器內立刻登錄次日同一時刻；停用或刪除即 `cancel()`。
- **為什麼不是** `setExactAndAllowWhileIdle()`：兩者都能穿透 Doze，但 `setAlarmClock` 額外（a）在狀態列與系統「下一個鬧鐘」顯示，使用者看得到、(b) 明確屬於「使用者要求的精確鬧鐘」而享有 Android 12+ 從背景啟動前景服務的豁免、(c) 不受 `setExactAndAllowWhileIdle` 每 9 分鐘一次的節流。
- **為什麼不是 WorkManager／JobScheduler**：不保證準時，可能延遲數分鐘到數十分鐘，不符 60 秒內開始的要求。
- **為什麼不是 `setRepeating`**：API 19 起不精確，且 DST／時區變更的處理不透明；自己登錄下一次更可控。
- **權限**：`USE_EXACT_ALARM`（API 33+，安裝即授予，不可撤銷）與 `SCHEDULE_EXACT_ALARM`（API 31–32，預設授予、可被使用者撤銷）。啟用時以 `canScheduleExactAlarms()` 檢查，為 false 時開 `ACTION_REQUEST_SCHEDULE_EXACT_ALARM` 設定頁並在介面說明後果。
- **下一次時刻的計算**抽成不依賴 Android API 的純 Java 類（一律用裝置預設時區），以 JUnit 測試釘住「已過→次日」「恰為同一分鐘→次日」「23:59」「跨月」「時區變更」等邊界，`gradlew :app:testDebugUnitTest` 執行。
  **實作時改用 `java.util.Calendar` 而非原訂的 `java.time`**：本專案 minSdk 為 24，而 `java.time` 需要 API 26，未啟用 core library desugaring 時會在 API 24／25 的裝置上直接崩潰。啟用 desugaring 會改變整個 App 的 D8 處理流程，代價大於此處所需；`Calendar` 自 API 1 起可用、同樣不依賴 Android API、同樣可在 JVM 測試，且台灣無日光節約，兩者在本用途下行為無差異。

### D2 觸發後：接收器 → `mediaPlayback` 前景服務

- 鬧鐘的 `PendingIntent` 指向 `BroadcastReceiver`，接收器只做三件事：登錄下一次、讀設定、`startForegroundService()`。播放邏輯全在服務內，避免接收器 10 秒限制。
- 服務為 **新類別**（不是擴充 `KeepAliveService`），`foregroundServiceType="mediaPlayback"`，需 `FOREGROUND_SERVICE_MEDIA_PLAYBACK`。通知用**獨立的 channel 與 id**，與下載通知（id 1）互不覆蓋。
- 服務持有 `PARTIAL_WAKE_LOCK`（上限＝結束時間＋緩衝）與 `WifiLock`；`onStartCommand` 收到新的 START 時若已在播放，只把結束時間更新為兩者較晚者（規格「重疊」情境），不重建播放器。
- 自動停止以 `Handler.postDelayed` 到結束時刻；「停止」按鈕的 `PendingIntent` 送 ACTION_STOP 回服務。
- **為什麼不是直接在接收器裡播**：接收器不能長時間存活；系統會在回傳後隨時回收程序。

### D3 播放器用 media3 ExoPlayer，不用 `android.media.MediaPlayer`

- 目標串流是無 Content-Length 的 icecast 型 ADTS AAC。`MediaPlayer` 對這類串流的表現依廠牌與版本不一（有的要等很久才起播、有的斷線不重連），而鬧鐘情境**沒有人在旁邊按重試**。ExoPlayer 對此成熟：可設定 `LoadErrorHandlingPolicy` 重試、支援 ICY、起播延遲可控。
- 成本：APK 約 +1.5 MB。可接受，本 App 已含 yt-dlp、ffmpeg 等大件。
- 音訊屬性 `USAGE_ALARM` + `CONTENT_TYPE_SPEECH`：走鬧鐘音量、勿擾模式仍會出聲（Android 預設允許鬧鐘），這是規格「鬧鐘語意」的實作依據。**替代案**：`USAGE_MEDIA` 走媒體音量 —— 靜音時不會響，與「鬧鐘」的預期相悖，不採。
- 音訊焦點請求 `AUDIOFOCUS_GAIN_TRANSIENT`：正在播的音樂暫停，結束後恢復。

### D4 來源解析：依頻道，官方 API → 該頻道上次成功 → 該頻道內建常數

```
  自訂頻道 ──────────────────────────────────────> 直接用其網址（不查 API）
  內建頻道  GET ChannelInfoBat（逾時 5 秒）
            └─ 找 name == 該頻道的 apiName ─> iosStream（https）優先，其次 androidStream
                 成功 -> 播放並寫入 last_good_url[頻道]
                 失敗 -> last_good_url[頻道] -> 該頻道的內建常數
```

內建常數（2026-09-17 自官方端點取得）：中廣新聞網 `https://stream.rcs.revma.com/fgtx07f3qtzuv`、中廣流行網 `https://stream.rcs.revma.com/s1zttsg3qtzuv`。

- 用 `HttpURLConnection` 即可（JSON 小、單次），不引入新的 HTTP 依賴；`usesCleartextTraffic` 已開，但一律優先 https。
- 內建常數集中於一個常數類，與 `NETWORK_PROBE_URL` 同樣附註解說明來源與日期。
- `last_good_url` **按頻道**存：兩個頻道各自退回，新聞網的後備不能拿去放流行網。
- **為什麼要問 API 而不是只寫死**：實測社群記錄的 key 與官方現行不同，key 會輪替；寫死等於某天早上無聲。
- **為什麼還要內建常數**：API 可能改版或下線；退回鏈末端必須有東西。

### D5 設定與狀態存在原生端 `SharedPreferences`（獨立檔 `avd_radio_alarm`）

- 內容：總開關、時間清單（JSON 陣列：id、HH:mm、enabled、durationMin）、自訂網址、`last_good_url`、上次結果（time、context、message、pendingJournal）。
- 插件方法：`getRadioAlarmConfig`、`setRadioAlarmConfig`（寫入後立即重新登錄全部鬧鐘）、`getRadioAlarmStatus`（下一次觸發、上次結果、權限狀態）、`testRadioAlarm`（試播 30 秒）、`stopRadioAlarm`、`consumeRadioAlarmJournal`（取出待寫入錯誤紀錄的摘要並清除 pending）。
- 前端**不**對這些鍵 `defineSetting`；設定區段開啟時呼叫 `getRadioAlarmConfig`，變更時整包 `setRadioAlarmConfig`。這正是 `config-persistence` MODIFIED delta 所允許並約束的形態。
- **替代案**：讓 Android 的儲存埠改成原生 Preferences，讓所有設定都能被原生讀到 —— 範圍太大且需遷移既有 localStorage 資料，不在本次。

### D6 重開機與時間變更：一個接收器接三個廣播

- `BOOT_COMPLETED`、`TIME_SET`、`TIMEZONE_CHANGED` → 讀設定 → 全部重新登錄（先 `cancel` 再 `set`）。需 `RECEIVE_BOOT_COMPLETED` 權限。
- 時鐘往前調越過某時刻時，「下一次」計算自然落到次日，不會補播（規格明訂）。

### D7 失敗處理與錯誤紀錄的延遞寫入

- 服務內自預定開始時刻起計時，累計 3 分鐘仍未進入 `STATE_READY` → 停止、發一則一般通知（非前景通知）說明原因、將摘要寫入 prefs 並標記 `pendingJournal=true`。
- 前端啟動時呼叫 `consumeRadioAlarmJournal`，有東西就 `reportError('早報鬧鐘', message)`（沿用既有錯誤紀錄流程，滿足 error-journal「未截斷原文」），寫完即清 pending，避免重複。
- **為什麼不即時寫**：錯誤紀錄住在 WebView 的 localStorage，觸發當下 WebView 多半沒在跑。

### D8 通知權限在首次新增鬧鐘時請求

- API 33+ 需 `POST_NOTIFICATIONS` 執行期權限。前景服務即使沒有此權限也照跑（只是通知不顯示），所以**播放不會因此失敗**，失去的是「停止」按鈕與失敗通知。介面依 `getRadioAlarmStatus` 回傳的權限狀態顯示說明與重新授權入口。
- 透過 Capacitor 的 `@Permission` 別名機制請求，不自己處理 requestCode。

### D9 介面：時間為第一層的鬧鐘卡片，正常時安靜

（D14 重構後的版本；原本「總開關 → 電台 → 時間」的兩層結構已被取代。）

```
  鬧鐘                                          [+ 新增]
  +-------------------------------------------------+
  | 06:00                              30分   [on]  |   <- 第一層：時間（點擊展開）
  |   一二三四五 · 中廣新聞網                        |      收合時的摘要
  +-------------------------------------------------+
  | 07:00                              30分   [on]  |
  |   六日 · 中廣流行網                              |
  +-------------------------------------------------+
    展開後：
    星期   [日][一][二][三][四][五][六]                <- 第二層
    頻道   (*) 中廣新聞網   ( ) 中廣流行網            <- 第三層
    時長   [- 30 +] 分                    [移除]

  頻道
  +-------------------------------------------------+
  | 中廣新聞網                                 [▸]  |   <- 直播鈕跟著頻道
  | 中廣流行網                                 [▸]  |
  +-------------------------------------------------+

  音量  ───────●────── 60%
  鬧鐘走鬧鐘音量，直播走媒體音量。                      <- 唯一保留的一行說明

  > 進階（預設收合）：試播、兩分鐘後試響、測試結果
```

- 以 `!isTauri()` 決定是否渲染（功能可用性的判斷，不是為了持久化判斷平台）。
- **正常時安靜、異常才說話**：系統登錄狀態只在「有啟用的鬧鐘但系統中一筆都沒有」時出現；上次播放結果只在失敗時出現；權限提示只在缺失時出現。一切正常的畫面只有清單、頻道、音量。
- **沒有不可逆操作**：移除一筆鬧鐘只是設定調整，不用 `danger` 色；不加二次確認。
- **展開與移除都要看得見**（實機回報「設了鬧鐘不知道怎麼取消」後補上）：卡片右側有 ▼／▲ —— 手機上沒有 hover，少了它使用者看不出卡片能點；移除是展開後底部一顆完整的「移除這筆鬧鐘」按鈕，不是角落的一個 `×`。「安靜」是指不說廢話，不是把操作藏起來。
- 狀態以**文字**表達，不引入新顏色。
- 前端純函式（時刻驗證、星期摘要、卡片摘要、含星期的「下一次」）放 service 模組並附 vitest。

### D11 音量分兩層：系統鬧鐘音量是上限，應用程式內的比例在其下縮放

實作後的追加範圍。原設計只寫「音量跟隨系統鬧鐘音量」，實際用起來有兩個缺口：使用者若覺得太大聲，只能去改**整台手機的鬧鐘音量**，連帶影響真正的鬧鐘；而早上被吵醒後打開 App 想調，按音量鍵調到的卻是媒體音量。

```
  系統鬧鐘音量（使用者的手機設定，本功能 MUST NOT 更動）
        ↓  上限
  應用程式內的比例 0-100%（player.setVolume，預設 100%）
        ↓
  實際輸出
```

- **用 `Player.setVolume(float)` 而非 `AudioManager.setStreamVolume`**：後者會改掉裝置的鬧鐘音量設定，使用者真正的鬧鐘會跟著變 —— 那是替使用者做了他沒要求的決定。前者只在本次播放的輸出上衰減，離開播放不留痕跡。
- **比例是單一全域設定，不做逐筆**：逐筆音量的用途難以想像（同一個人、同一個房間、相隔一小時），而每多一個逐筆欄位，時間列就更擠一分 —— 那一列已經在窄畫面上換行了。
- **播放中變更立即生效**：設定寫回後，若服務正在播放，插件送一則 `ACTION_SET_VOLUME` 給服務，服務自己重讀設定並套用。不重建播放器。
- **音量鍵**：`Activity.setVolumeControlStream(STREAM_ALARM)` 只在播放期間套用，停止後還原為 `USE_DEFAULT_STREAM_TYPE` —— 否則 App 平常的音量鍵行為會被改掉。Activity 於 `onResume` 依目前播放狀態決定，服務則在開始與停止時主動通知 Activity（以 WeakReference 持有，Activity 不存在時什麼都不做）。

**替代案：漸強（前 30 秒由小聲升到設定音量）** —— 使用者在此次範圍中未選擇，未實作。若日後要加，位置在 `preparePlayer` 之後以 Handler 分段調整 `setVolume`，與本決策不衝突。

### D12 手動直播是第三種模式，不是第二條播放路徑

實作後的追加範圍（使用者要求「加個直播鈕」，位置在電台那一排）。

播放服務因此從「一種行為＋一個 isTest 旗標」改為**三種模式**，共用同一個服務、同一套來源解析、同一套重試與通知：

```
  模式    音訊語意      長度              失敗的處理
  alarm   鬧鐘音量      該筆鬧鐘的時長    發通知 + 留給錯誤紀錄
  test    鬧鐘音量      30 秒             只留紀錄（使用者正看著畫面）
  live    媒體音量      3 小時上限        只留紀錄
```

- **紅線 2 仍然成立**：`ACTION_START` 的送出點仍只有接收器與插件，`new ExoPlayer.Builder` 仍只有一處。模式是**參數**，不是分岔的實作 —— 分岔才會出現「試播成功、早上不響」。
- **試播刻意維持鬧鐘音量**：它的用途就是驗證早上會不會響，換成媒體音量就驗不到真正要驗的東西。
- **手動直播改走媒體音量**：鬧鐘能蓋過靜音與勿擾，是因為使用者要求被叫醒；手動按播放並沒有這個要求，在會議中蓋過靜音放出聲音是錯的。代價是同一個功能有兩種音量來源，故介面在播放中必須顯示是哪一種（`describePlaybackState`）——否則使用者會對著沒反應的音量鍵發愣。
- **不受總開關約束**：「現在想聽廣播」與「明天早上要被叫醒」是兩件事，為了聽廣播而去開鬧鐘並不合理。
- **有上限而非無限**：「聽到我按停止為止」的正確實作不是無限 —— 忘了關的前景服務會整天持有 WakeLock 與 WifiLock。3 小時上限加上通知載明預計停止時間，要續聽再按一次。
- **曾評估「全部統一用媒體音量」，明確不採**（使用者提出後一併評估）。統一確實能簡化規格、介面與程式，但代價落在鬧鐘上：媒體音量很容易被調到 0（前一晚聽完東西關掉就是），部分廠牌的睡眠模式也會連媒體一起靜音 —— 而「早上完全沒聲音」正是本功能最糟的失敗方式，整個 change 的失敗窗、失敗通知、錯誤紀錄都是為了避免它。
  若日後仍想統一，方向 MUST 是**全部走鬧鐘音量**（同樣簡化，且不犧牲會不會響），而非全部走媒體音量。手動直播因此得到的較大音量，由播放中已切到 `STREAM_ALARM` 的音量鍵當場調整。
- **介面需要輪詢**：播放在服務裡進行，前端不會被通知。設定開著時每 3 秒讀一次狀態；少了它，播放結束後按鈕會一直停在「停止」，試播失敗的原因也不會出現在狀態那一行（規格要求試播即時顯示結果）。關掉對話框即停 —— 這不是背景工作。
- **新增一個操作字元 `stop: '■'`**：方形即停止，與三角形向右即播放同一套準則。它與 `play` 出現在同一個位置、依狀態互換，故不會同時出現而需要互相區辨；`visualLanguage.spec.ts` 的「只有兩顆刪除共用字元」與「可復原動作不得歸為不可逆」兩條測試已同步。

### D13 可驗證性本身就是功能的一部分

實作後的追加範圍。使用者問「AVD 關掉就沒用了吧？」—— 而當時的答案是：**設計上不會，但你無法驗證**。這才是真正的缺口。

盤點現有的驗證手段後發現它們都不驗這件事：

| 既有手段 | 實際驗證了什麼 | 沒驗到什麼 |
| --- | --- | --- |
| 試播 30 秒 | 來源解析、播放器、音訊輸出 | **整段鬧鐘機制** —— 它直接啟動服務 |
| 「下一次觸發：明天 06:00」 | 什麼都沒有 | 它是**本程式自己算的**；系統中一個鬧鐘都沒有時，它照樣這樣顯示 |

第二列尤其糟：它讓介面在**最該示警的情況下看起來最正常**。

因此加兩件事：

- **向系統回讀的登錄狀態**。以 `PendingIntent.FLAG_NO_CREATE` 逐一探測我們登錄過的 id，回傳 null 即代表那筆已不存在（被取消，或整個 App 被強制停止過）。另以 `AlarmManager.getNextAlarmClock()` 取裝置的下一個鬧鐘，並用 `getShowIntent().getCreatorPackage()` 判斷是否為本程式。
  後者回傳的是**整台裝置**的下一個鬧鐘（可能是使用者的時鐘 App 的），故「不是我們的」不代表我們沒登錄 —— 介面的措辭必須照這個語意，不能謊稱那個鬧鐘是自己的。
- **一次性的自我測試鬧鐘**（兩分鐘後）。走與早上完全相同的路徑：`setAlarmClock` → `RadioAlarmReceiver` → 前景服務。使用者按完可以把 App 完全關掉再等它響。
  - **不進設定**：另存於 `self_test_at`，不進 `scheduled_ids` —— 否則使用者在等待期間改任何設定，`rescheduleAll` 就會把它一併取消。也因此不會在時間清單留下殘留項目。
  - **不看總開關**：它驗的是機制，不是使用者的排程；接收器在自我測試分支直接播放，不查設定。
  - **響起的事實要持久化**（`self_test_fired_at`）。這是整個設計最關鍵的一點：這筆記錄由**接收器**寫入，而接收器只有在系統把已經不在前景的程序叫起來時才會執行。使用者關掉 App、回來看到這一行，就得到了他要的那個答案 —— 而不是我說「設計上不會」。

### D14 模型翻轉：鬧鐘是主體，頻道是它的屬性

實作後的重構（使用者要求「第一層時間、第二層星期、第三層頻道」）。原本的結構是**電台為容器、時間在其下**；使用者要的是所有鬧鐘 App 的樣子 —— 一筆鬧鐘就是一筆鬧鐘，它「在幾點、哪幾天、放哪一台」。

```
  Alarm {                              Channel {
    id            穩定識別                id       'bcc-news' | 'bcc-pop' | 自訂
    time          HH:mm                  name     顯示名稱
    weekdays      7 位元遮罩（日..六）     source   bcc: { apiName }   <- 向官方 API 依名稱解析
    channelId     -> Channel.id                    url: { url }       <- 自訂串流
    durationMin   1..180
    enabled
  }
  Config { alarms[], channels[], volumePercent, schemaVersion }
```

- **平面而非巢狀**。「同一時間依星期指定不同頻道」在平面模型就是兩筆鬧鐘（06:00 一至五 新聞、06:00 六日 流行），表達力相同，但「新增」只有一種動作。巢狀（時間 → 星期組 → 頻道）要分「新增時間」與「在某時間下新增星期組」兩種，操作繞。
- **因此拿掉「同一時刻不得重複」**。排程本來就以 alarm id（而非時刻）組 requestCode 與 data URI —— 這正是當初用 id 的好處，兩筆同時刻的鬧鐘不會互相覆蓋。
- **星期用 7 位元遮罩，預設全選，至少一天**。空遮罩在鬧鐘 App 通常代表「只響一次」，對廣播用處不大且容易被誤認為壞了；介面不允許取消最後一天，原生端 `fromJson` 遇到空遮罩則校正為全選。`nextTrigger` 自今天起往後最多找 7 天，取第一個「時刻未過且星期符合」者。
- **拿掉總開關**。每筆鬧鐘自有開關，總開關是第四個概念。紅線 1（升級後不會無預警響）改由「清單預設為空」達成；「首次開啟預填 06:00／07:00」隨之消失，改為新增時的預設值。
- **頻道的彈性放在模型，介面先只列兩個**。中廣官方那支 API 回傳五個頻道，內建頻道只差 `apiName`；自訂頻道是 `url`。新增頻道的介面本次不做，但 `Channel` 的形狀與播放路徑已支援。頻道被移除時，指向它的鬧鐘改指第一個內建頻道 —— 不讓鬧鐘因此消失。
- **遷移只做一次**，以 `schemaVersion` 判斷：舊 `entries` → 每筆一個 Alarm（星期全選、頻道 bcc-news、時長與啟用沿用）；舊 `customStreamUrl` 非空 → 建一個自訂頻道並讓所有遷移的鬧鐘指向它（舊網址對所有時間生效，遷移後行為相同）；舊 `masterEnabled=false` → 全部停用。遷移後寫入新 schemaVersion，MUST NOT 再次執行。
- **直播鈕跟著頻道走**，不再掛在鬧鐘上；試播播第一個內建頻道；自我測試不看頻道（它驗機制）。
- **移除的東西**：`describeStationSummary`、電台那一層、串流網址欄位（其資料遷移進自訂頻道，介面暫不提供編輯）、總開關相關的插件欄位與前端流程。舊測試一併刪除，不留死碼。

### D15 本地檔案頻道：一個頻道是一份複製進私有目錄的播放清單

實作後的追加範圍（使用者要求「鬧鐘除了串流，可加本地的 mp4 或 mp3」）。

D14 已把頻道做成鬧鐘的屬性，`Channel.kind` 目前有 `bcc`（向官方 API 解析）與 `url`（自訂串流）兩種；本地檔案是**第三種 kind `file`**。鬧鐘模型一個欄位都不動，schemaVersion 也不升：舊版 App 的 `parseChannels` 遇到不認識的 kind 會剔除該頻道，指向它的鬧鐘落回第一個內建頻道 —— 降版安全。

但「播檔案」與「播直播」在四處行為不同，這四處各自是一個決定：

```
                    直播（bcc / url）              本地檔案（file）
  來源             觸發時解析網址，走網路           選檔時複製進私有目錄，觸發時讀本機
  播完             不該結束；結束＝斷線，重連       會結束；結束＝下一首，循環到時長
  失敗             連不上，3 分鐘窗內重試           讀不到，第 0 秒即知；不重試、不出聲
  影像軌           無                               mp4 有；停用，只解音訊
```

#### 來源：系統選檔器多選，選完複製進 `filesDir/radio_alarm/<channelId>/`

- **選檔用 `ACTION_OPEN_DOCUMENT` 加 `EXTRA_ALLOW_MULTIPLE`**，MIME 限 `audio/*` 與 `video/*`。這是一個新的插件方法（`pickRadioAlarmFiles`），以 Capacitor 的 `startActivityForResult` 機制回傳；不自己管 requestCode。
- **複製而非引用**。整個 change 最在意的失敗是「早上完全沒聲音」，而直接引用外部檔案有兩條會走到那裡的路：
  - 引用公開目錄（如 AVD 自己下載到 `Music/`、`Movies/` 的檔）：Android 10+ 的 scoped storage 下，App 重裝或清除資料即失去這些檔案的擁有權，要再讀就得申請 `READ_MEDIA_AUDIO`／`READ_MEDIA_VIDEO`。
  - 引用選檔器給的 `content://`（`takePersistableUriPermission`）：可跨重開機，但檔案被使用者移走、改名、刪除，或 SD 卡被拔，6 點就讀不到。
  複製一份進私有目錄後，兩條路都堵掉：私有目錄不需任何權限、不受使用者整理檔案影響、隨 App 解除安裝一併清除。代價是多佔一份空間 —— 鬧鐘用的幾首歌以 MB 計，可接受。
- **複製在選檔當下、於背景執行緒完成**，前端顯示進度或忙碌狀態；全部複製完才寫入設定。複製到一半失敗（空間不足、來源不可讀）則整個頻道不建立並提示原因，MUST NOT 建出一個只有部分檔案的頻道 —— 使用者不會知道少了哪首。
- 檔名保留原始顯示名稱（自 `OpenableColumns.DISPLAY_NAME` 取得）供介面列出；磁碟上的檔名另以 `序號_原名` 存，避免同名覆蓋。
- **AVD 自己下載的檔案**（任務卡片上「設為鬧鐘」）是可能的第二個入口，底層仍走同一個複製流程。本次不做，記於 Non-Goals。

#### 播完：一個頻道是一份有序清單，固定照選取順序，循環到時長結束

- `Channel.source` 對 `file` 這種 kind 是**有序的檔案路徑清單**（JSON 陣列），對 `bcc` 與 `url` 維持單一字串不變。原生端以 `Channel.files` 另存清單、`source` 留作顯示用摘要；前端型別以 `kind` 做 discriminated union。
- **為什麼是清單而不是一檔一頻道**：鬧鐘每天早上放同一首 4 分鐘的歌循環 30 分鐘，一週就聽膩了；多選的價值就在輪播。一檔一頻道也會讓頻道列很快變長。
- **順序固定照選取順序，不隨機**。少一個概念；想換順序就重建頻道。
- **循環到時長結束**，不是播一次就停：鬧鐘的語意是「叫醒我直到我按停止」，播一次 4 分鐘就靜下來的鬧鐘不像鬧鐘。時長欄位維持原意，使用者想只放一遍就把時長調短。手動直播（live 模式）按同一個檔案頻道時照 `LIVE_MAX_MS` 上限循環，不另做規則。
- 實作上以 ExoPlayer 的**多個 `MediaItem` 加 `REPEAT_MODE_ALL`** 達成，不自己在 `STATE_ENDED` 裡換歌。現有的「`STATE_ENDED` → 重連」只對直播成立，file 模式下 `STATE_ENDED` 理論上不會出現（REPEAT_MODE_ALL），出現了也只記錄不重試。

#### 失敗：讀不到就是失敗，不出聲、不退回電台

- 曾評估「檔案讀不到時改播第一個內建頻道」（依 D4「退回鏈末端必須有東西」的精神），**使用者明確不採**：使用者選了本地檔案就是不想聽電台，早上突然放出新聞比沒響更令人困惑。
- 因此 file 頻道**沒有退回鏈**。觸發時逐一檢查清單中的檔案是否存在且可讀，一個都沒有即以 `fail()` 走既有失敗流程：發失敗通知、寫上次結果、標記 `pendingJournal` 供下次開 App 寫入錯誤紀錄，訊息載明頻道名稱與「檔案不存在」。部分檔案不存在則跳過那些、播其餘，並在上次結果留下「有 N 個檔案讀不到」的成功紀錄（成功但有話要說）。
- 3 分鐘失敗窗對本機檔案沒有意義；file 模式下 `giveUp` 仍照排（無害），但實際的失敗判定在建播放器前就完成了。
- 複製進私有目錄後，這條路實際上只在使用者手動清除 App 資料、或磁碟損毀時走到；它的存在是為了讓「沒響」永遠有一則說明，而不是因為它常發生。

#### 影像軌：mp4 只解音訊

- ExoPlayer 沒有 surface 也會**把影像軌解碼再丟掉**，6 點時 CPU 白跑整段時長。file 模式建播放器時以 `TrackSelectionParameters` 停用 `C.TRACK_TYPE_VIDEO`，只留音訊。這一行不寫，功能看起來正常但耗電。
- 不因此換用純音訊的 `RenderersFactory`：那會讓 `new ExoPlayer.Builder` 依模式分岔，違反紅線 2 的精神（單一建構點）。停用軌道是**參數**，不是分岔。

#### 被牽動的既有程式碼

- 前端 `normalizeConfig` 目前把 kind 不是 `'url'` 的**一律當 `'bcc'`**：file 頻道進來會被誤標為內建頻道，然後拿檔名去問中廣 API。MUST 改為三值判斷，未知 kind 剔除。
- 原生端 `isValidStreamUrl` 只認 http(s)；file 頻道另以「清單非空且每個路徑落在私有目錄下」驗證，MUST NOT 接受私有目錄以外的路徑（那正是複製要避免的東西）。
- `RadioStreamResolver.resolve` 對 file 回傳清單而非單一網址；服務端 `preparePlayer` 的簽章隨之改為接受 `List<MediaItem>`，bcc／url 傳一個元素的清單。WifiLock 照拿，無害且不必分岔。
- 通知標題用 `channel.name`：file 頻道的名稱預設為**第一個檔案檔名的前段**（去副檔名、最多 16 字、超過加「…」），使用者可改名。原本是「第一個檔名 等 N 個檔案」—— 下載的檔名多是整句影片標題，實機上一列被撐成三行；使用者要求「只抓前面當題，明細要點進去」後改為此。檔案數在列上另有一格小字。
- **這是第一個「新增頻道」的介面**。規格原寫「MAY 不提供新增自訂頻道的介面」，加了 file 就非做不可：頻道列多一顆新增（開選檔器）；非內建頻道的列上只有短標題、檔案數與 `›`，**點進**對話框才看到名稱欄、依播放順序的檔案清單（可捲動）與移除；移除時刪掉私有目錄下該頻道的資料夾，指向它的鬧鐘落回預設頻道（既有邏輯）。鬧鐘卡片裡的頻道單選標籤同樣截斷。自訂串流網址（url kind）的新增介面**仍不做**，維持只由舊資料遷移產生。
- 遷移不需變動：schemaVersion 維持 2，新 kind 的頻道只會由新版寫入。

**不採的替代案一覽**：一檔一頻道（見上）、隨機順序（見上）、讀不到退回電台（使用者不採）、直接引用 `content://` 不複製（見「來源」）、播一遍即停（見「播完」）。

### D16 股票報價頻道：抓富果報價、組稿、文字轉語音合成成檔，再交給同一個播放器

實作後的追加範圍（使用者要求「頻道增加用富果 API，選擇多支股票，口說播放」）。第四種 kind `stock`。

```
  觸發  ->  逐支 GET api.fugle.tw/.../intraday/quote/{symbol}（X-API-KEY，各 5 秒）
        ->  StockReportScript.build()：一段要念的繁體中文（純函式）
        ->  RadioTts.synthesizeToFile()：TextToSpeech 合成成 cacheDir/radio_alarm_tts/report.wav
        ->  preparePlayer(Resolution{ [report.wav], local=true })   <- 與檔案頻道完全相同的路徑
```

- **合成成檔而不是直接 `speak()`**：讓股票頻道與直播、本地檔案走同一個 ExoPlayer —— 鬧鐘音量、音訊焦點、通知、時長、循環、停止全部沿用，不必為 TTS 另寫一套音訊語意（紅線 2）。代價是多一步寫檔，幾十 KB 的 wav 可忽略。
- **循環到時長結束**，與檔案頻道一致：一段報價約 20–40 秒，使用者把時長設 1–3 分鐘就是「念幾遍」。
- **口說稿以「念出來聽得懂」為準**：百分比寫「百分之 1.01」不寫「1.01%」（引擎對 % 念法不一）、數字去尾零、每支一句、開場念頻道名與資料日期、收盤與否決定「收盤」或「目前」。純函式，JUnit 釘住。
- **全部抓不到時仍要念**：念「無法取得股價」加原因（金鑰未設、連不上、代號錯），同一原因只念一次。鬧鐘的第一要務是把人叫醒；一片安靜是最糟的失敗（與 D7 同源）。但這次的結果**記為失敗**（`stockFailureMessage`）而非「播放完成」，下次開 App 才看得到原因。部分失敗則念成功的、再念「另有 N 支無法取得」。
- **股票清單允許為空**：空頻道觸發時念「尚未加入任何股票」。不剔除的理由：介面流程是「先建頻道、再進明細加股票」，剔除會讓剛建的頻道消失。
- **金鑰是全域設定** `RadioAlarmConfig.fugleApiKey`：存原生端（觸發時 WebView 沒在跑），所有股票頻道共用；介面放在股票頻道明細裡（第一次建股票頻道的人在這裡才需要它），密碼欄不回顯。沒金鑰不發請求，直接以「尚未設定金鑰」失敗並念出。
- **加入股票時先查一次**（插件 `lookupStock`，與觸發同一套查詢與解析）取名稱與現價，讓使用者確認代號沒打錯；查不到仍可加入（沒名稱），早上會念出實際狀況。
- **中文語音**：依序試 `zh-TW`、任何中文；都沒有即 `fail("裝置沒有中文語音…")`，走失敗通知。Android 11 起需在 Manifest 宣告 `TTS_SERVICE` 的 `<queries>`，否則 `TextToSpeech` 找不到引擎 —— 這一條漏了功能會靜默失敗。
- **富果 API 端點與欄位**（2026-09-21 依官方文件確認）：`name`、`closePrice`、`lastPrice`、`previousClose`、`change`、`changePercent`、`date`、`isClose`。價格取 closePrice → lastPrice → previousClose 第一個大於 0 者；`change`／`changePercent` 缺時自前收計算。錯誤回應（401／404／429）各有可念的原因，不會被念成「0 元」。
- **替代案：直接 `TextToSpeech.speak()` 用 STREAM_ALARM** —— 少一步寫檔，但停止、時長、音量比例、音訊焦點、通知都要另寫一份，且無法循環；不採。
- **替代案：金鑰逐頻道** —— 同一個人只會有一把金鑰，逐頻道只是多打幾次；不採。

### D10 試播走與正式觸發完全相同的路徑

- `testRadioAlarm` 直接以「結束時間＝現在＋30 秒」啟動同一個服務，來源解析、重試、通知全部一致。這樣試播成功就代表早上會成功，不會出現「試播用 A 路徑、鬧鐘用 B 路徑」的假安心。

## Risks / Trade-offs

- **[廠牌省電機制殺程序（小米、華為、OPPO 等）]** → `setAlarmClock` 是各家最少干預的鬧鐘型別；介面在偵測到非原生 Android 廠牌時提示「若未響起，請允許本 App 自啟動／關閉電池最佳化」，並提供 `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 入口。無法保證所有廠牌，於 proposal 假設中已標示。
- **[官方 API 改版或串流 CDN 更換]** → 三層退回鏈；使用者可填自訂網址即時繞過，不需等新版。
- **[6 點 Wi-Fi 因 Doze 斷線、資料網路慢]** → WifiLock ＋ 3 分鐘重試窗；仍失敗則通知並記錄，不會無聲無息。
- **[Android 12+ 從背景啟動前景服務被拒]** → 精確鬧鐘屬豁免清單；若某版本仍拒絕，接收器捕捉 `ForegroundServiceStartNotAllowedException` 並改以 `setAlarmClock` 的 `showIntent` 拉起 Activity 再啟動服務（實作時以實機驗證是否需要此後路）。
- **[鬧鐘音量被使用者設為 0]** → 與系統鬧鐘同樣的限制；介面說明「音量跟隨系統鬧鐘音量」。不主動改音量（避免驚嚇）。
- **[ExoPlayer 增加 APK 體積、引入新依賴]** → 接受；鎖定版本，`gradlew` 離線建置需先同步一次依賴。
- **[錯誤紀錄延後到下次開 App 才寫]** → 通知已即時告知；紀錄的時間欄位用實際發生時間而非寫入時間，事後可對得上。
- **[日後若上架 Play，`USE_EXACT_ALARM` 需改申請]** → 目前側載，不影響；若上架再改為 `SCHEDULE_EXACT_ALARM` 引導授權，排程程式碼不變。

## Migration Plan

1. 新增功能預設**總開關關閉**，升級不改變任何既有行為；使用者手動開啟後才登錄鬧鐘。
2. 關閉總開關即取消全部鬧鐘並停止播放；解除安裝時 `SharedPreferences` 隨之刪除，無殘留。
3. 回滾：退回上一版 APK 即可，本 change 不改任何既有設定鍵或資料格式。
