## MODIFIED Requirements

### Requirement: 以 uploads 播放清單擷取頻道新片

設定有效金鑰時，系統 MUST（必須）以 YouTube Data API 擷取該頻道的上傳影片清單，回傳的資料 MUST（必須）轉換為上層共用的內部影片結構，使新片判定、關鍵字篩選與錨點計算無須知道資料來自哪個端點。

每支影片 MUST（必須）帶有影片識別碼、標題與**精確發布時間**。API 通道 MUST NOT（不得）以當下時間替代缺失的發布時間。

系統 MUST（必須）能由頻道識別碼取得其 uploads 播放清單識別碼。若採用識別碼前綴轉換的慣例而該清單不存在，系統 MUST（必須）改以查詢頻道詳細資料的方式取得正確的 uploads 播放清單識別碼，MUST NOT（不得）逕行判定該頻道無效。

**擷取請求 MUST（必須）只向服務索取系統實際會讀取的欄位。** 索取而後丟棄的欄位在行動裝置上同時付出傳輸與解析兩份成本，而每輪每個頻道都要付一次。此約束對使用者可觀察的行為是回應時間，對系統則是一條硬性耦合：**所索取的欄位集合與程式實際讀取的欄位集合 MUST（必須）一致**，任一邊變動時另一邊 MUST（必須）同步 —— 少索取一個仍在讀的欄位，該欄位會靜默變成未定義而非報錯。

#### Scenario: 成功以 API 取得新片

- **WHEN** 已設定有效金鑰且 API 正常回應
- **THEN** 系統 MUST 回傳該頻道最新影片清單，每支帶有影片識別碼、標題與精確發布時間
- **AND** 系統 MUST NOT 為頻道追蹤發出任何非 API 的擷取請求

#### Scenario: 請求不索取用不到的欄位

- **WHEN** 系統為某頻道發出影片清單擷取請求
- **THEN** 該請求 MUST 明確限定所需欄位，MUST NOT 索取系統不會讀取的欄位
- **AND** 回應中每一個被索取的欄位 MUST 至少有一處程式會讀取它

#### Scenario: 欄位限定不得改變擷取結果

- **WHEN** 對同一頻道分別以「限定欄位」與「不限定欄位」發出請求
- **THEN** 兩者解析後得到的影片識別碼、標題與發布時間 MUST 完全相同
- **AND** 限定欄位 MUST NOT 使任何影片被略過或其發布時間退化為缺失

#### Scenario: uploads 播放清單以慣例推導失敗

- **WHEN** 由頻道識別碼推導出的 uploads 播放清單識別碼查詢回報不存在
- **THEN** 系統 MUST 改以查詢頻道詳細資料取得正確的 uploads 播放清單識別碼並重試
- **AND** 僅當該查詢亦確認該頻道不存在時，系統才 MUST 將其視為頻道層級的錯誤

#### Scenario: API 回傳的影片缺少發布時間

- **WHEN** API 回傳的某支影片不帶可解析的發布時間
- **THEN** 系統 MUST NOT 以當下時間替代
- **AND** 該影片 MUST 依既有「缺少精確發布時間」的錨點守門規則處理

### Requirement: 直播狀態改以批次查詢

設定有效金鑰時，系統 MUST（必須）以單次 API 請求批次查詢多支影片的直播狀態，取代逐支影片各自發出一次查詢。單次批次請求 MUST（必須）最多涵蓋 50 支影片；候選影片超過 50 支時 MUST（必須）分批，每批仍為單一請求。

批次查詢的對象 MUST（必須）沿用既有的候選收斂規則 —— 只查詢已通過該頻道關鍵字篩選的候選影片，MUST NOT（不得）為未命中關鍵字的影片發出查詢。

批次查詢的請求 MUST（必須）只索取直播狀態判定實際會讀取的欄位，與「以 uploads 播放清單擷取頻道新片」的欄位約束一致。

#### Scenario: 候選影片少於單批上限

- **WHEN** 某輪有 8 支通過關鍵字篩選的候選影片需判定直播狀態
- **THEN** 系統 MUST 以單一 API 請求取得全部 8 支的狀態
- **AND** 系統 MUST NOT 逐支發出 8 次查詢

#### Scenario: 候選影片超過單批上限

- **WHEN** 某輪有 120 支候選影片需判定直播狀態
- **THEN** 系統 MUST 分為 3 批，每批以單一請求涵蓋最多 50 支

#### Scenario: 未命中關鍵字的影片不進入批次

- **WHEN** 某輪有影片符合既有新片條件但未命中該頻道關鍵字
- **THEN** 該影片 MUST NOT 被納入任何直播狀態批次查詢

#### Scenario: 批次查詢不索取用不到的欄位

- **WHEN** 系統發出直播狀態批次查詢
- **THEN** 該請求 MUST 只索取影片識別碼與直播狀態判定所需的欄位
- **AND** 三態判定（直播中或未開播／非直播／無法判定）的結果 MUST 與未限定欄位時完全相同

## ADDED Requirements

### Requirement: 頻道追蹤的 API 請求須有逾時上限

頻道追蹤發出的每一個 API 請求 MUST（必須）有逾時上限，且該上限 MUST（必須）在所有支援的平台上皆生效。

此要求的必要性來自移除備援後的失敗形狀：追蹤只剩單一通道，一個永不回應的請求會擋住整輪檢查，而使用者看到的是一個永不結束的進行中狀態 —— 那比明確失敗更糟，因為它無法被察覺、也無法被排查。

逾時 MUST（必須）產生**可辨識**的錯誤，使其與「服務明確回報失敗」可區分：兩者的意涵不同，前者代表這一輪沒有得到答案，後者代表服務給了答案而答案是失敗。逾時 MUST（必須）依既有規則計入該頻道的失敗，MUST NOT（不得）使該頻道被當作「沒有新影片」。

#### Scenario: 請求逾時不會無限等待

- **WHEN** 某個頻道的擷取請求在逾時上限內未收到回應
- **THEN** 系統 MUST 中止該請求並將其視為該頻道的失敗
- **AND** 系統 MUST 繼續處理其餘頻道，MUST NOT 停在該頻道上無限等待

#### Scenario: 逾時與服務回報的失敗可區分

- **WHEN** 一次擷取因逾時中止，另一次因服務回報錯誤而失敗
- **THEN** 兩者產生的錯誤 MUST 可被區分
- **AND** 逾時 MUST NOT 被歸類為配額耗盡或金鑰無效 —— 那會觸發不該觸發的抑制

#### Scenario: 逾時不得被當成沒有新影片

- **WHEN** 某頻道的擷取請求逾時
- **THEN** 系統 MUST NOT 將該頻道視為「已檢查且沒有新影片」
- **AND** 該頻道的時間錨點 MUST NOT 因這次逾時而推進

#### Scenario: 各平台皆有逾時

- **WHEN** 同一個永不回應的請求分別發生於 Windows 與 Android
- **THEN** 兩個平台 MUST 皆在各自的逾時上限內中止該請求
- **AND** MUST NOT 有任何平台缺少逾時而無限等待
