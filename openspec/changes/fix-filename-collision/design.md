## Context

動機與缺陷說明見 `proposal.md`。本節僅補充實作所需的現況事實。

**兩端的檔名主體是同一段邏輯的兩份實作，且都截到 30 字元：**

```ts
// DownloadService.ts:622-626
let cleanFileName = fullTitle.replace(/[\\/:*?"<>|]/g, '_');
if (cleanFileName.length > 30) cleanFileName = cleanFileName.slice(0, 30);
```

```java
// YoutubeDlPlugin.java:795-798
cleanTitle = videoTitle.replaceAll("[\\\\/:*?\"<>|]", "_");
if (cleanTitle.length() > 30) cleanTitle = cleanTitle.substring(0, 30);
```

**發布時間在兩端都已經取得**，只是沒有用於檔名：

- Windows：自 `.info.json` 讀出 `timestamp` / `upload_date`，經 `formatPublishTime` 產生 `pubTimeStr`。
- Android：v1.0.67 改為 `--dump-json` 後同樣拿得到 `timestamp`，用於任務標題顯示。

因此①不需要新增任何網路往返或資料來源，只是把既有資料接進檔名。

**碰撞處置的現況差異**：Windows 於 `DownloadService.ts:639-644` 以 `while (await exists(...))` 遞增；Android 於 `YoutubeDlPlugin.java:835-838` 直接 `throw`。

## Goals / Non-Goals

**Goals**

- 標題相同、發布時間不同的影片能各自存檔並全數成功。
- 碰撞在兩平台都是「自動改名」而非「失敗」。
- 檔名仍可辨識 —— 使用者從檔案總管就能看出是哪一支。

**Non-Goals**

- 不重構兩端重複的檔名邏輯為單一共用實作。兩者分屬 TS 與 Java、執行環境不同，強行共用需要跨語言的規則同步機制，成本高於收益；改以測試釘住規則。
- 不改變真正的「同一支影片重複加入」判定 —— 那由批次流程既有的 `existingUrls` 過濾負責。
- 不追溯處理磁碟上的既有檔案。

## Decisions

### D1. 時間格式採 `__yyyyMMdd_HHmmss`，緊接於截斷後的標題之後

```
#ちいかわ #chiikawa #吉伊卡哇__20260629_035012.mp4
```

**為何用雙底線分隔**：單底線在標題內容中很常見（非法字元被替換成 `_`），雙底線讓「標題」與「時間戳」的界線在肉眼與日後可能的解析上都清楚。

**為何不用 `2026-06-29 03:50:12` 這種可讀格式**：冒號是 Windows 的非法檔名字元，空白在跨平台的腳本處理中易生麻煩。`yyyyMMdd_HHmmss` 無分隔符爭議且天然可排序。

**為何接在截斷之後而非之前**：檔案總管與多數清單預設以名稱排序，時間在前會讓同一創作者的作品依時間散開；標題在前則同名作品聚在一起、時間為次序。後者較符合「找某一支影片」的使用方式。

**時間取影片的發布時間而非下載時間**：下載時間對使用者無意義，且同一批下載的數十支影片會落在極相近的秒數內，唯一性反而變差。

### D2. Android 由「拋例外」改為「遞增改名」，與 Windows 對齊

Android 現行的重複偵測分兩層（MediaStore 查詢 + 檔案系統檢查），兩層都只是為了判斷「要不要拋例外」。改為同一組檢查用於**找出下一個可用名稱**：檢查 `base.ext`，占用則試 `base_1.ext`、`base_2.ext`，直到可用。

**為何不乾脆移除重複檢查**：仍需要它來避免覆蓋既有檔案。MediaStore 那一層也要保留 —— Android 的媒體庫可能已登錄某個檔名而檔案系統路徑不同。

**遞增上限**：設一個合理的嘗試次數（例如 100）以避免病態情形下的無窮迴圈，超過則退回附加時間戳的隨機後綴。Windows 端現行的 `while` 迴圈同樣缺少上限，一併補上。

### D3. 純函式抽出並以測試釘住規則

檔名組成規則抽為 `buildDownloadFileName(title, publishTime)` 置於既有的 `src/services/parseScope.ts` 同層（新檔 `src/services/fileNaming.ts`），不依賴平台 API，可被 vitest 引用。

Java 端維持獨立實作，但以測試中列舉的案例作為對照表寫入註解，使兩端規則的差異在 code review 時可見。這是承認 Non-Goals 中「不強行共用」後的補償措施。

### D4. 「檔案已存在 (重複)」納入 `PERMANENT_DOWNLOAD_ERRORS`

`matchPermanentError` 目前將訊息轉小寫後比對英文片語。中文訊息不受大小寫影響，直接加入清單即可。

**為何在①②之後仍要加**：清單的意義是「確定性錯誤不重試」這條通則，不是逐一列舉已知錯誤。若日後某條路徑重新引入此錯誤，通則應自動生效。

## Risks / Trade-offs

- **[Risk] 檔名變長可能觸及路徑長度上限** → 時間戳固定 17 字元（`__` + 15），標題已截至 30，加副檔名後檔名約 51 字元，遠低於兩平台的上限。子資料夾路徑（`{頻道}/{清單}`）本就存在且未變。
- **[Risk] 使用者既有的檔案整理習慣被打亂** → 已於 proposal 標記為對磁碟檔名的 BREAKING。既有檔案不動，只有新下載採新格式，兩種格式會在同一資料夾並存一段時間。此為使用者明確選擇的方案。
- **[Risk] Android 的 MediaStore 查詢在遞增迴圈中被呼叫多次，可能拖慢** → 碰撞在①之後應極罕見，迴圈通常一次就結束。
- **[Trade-off] 兩端維持各自的檔名實作** → 規則漂移的風險由 D3 的測試與對照註解降低，但無法完全消除。這是刻意以成本換取的取捨。

## Migration Plan

無資料格式或設定變動。既有檔案不受影響，回退即 `git revert` —— 回退後新下載恢復舊命名，期間產生的新格式檔案仍可正常播放與管理。

三個項目彼此獨立可分批合入：③ 最單純，① 需兩端同步，② 只動 Android。

## Open Questions

- **標題截斷長度 30 是否仍合適。** 加上時間戳後檔名總長仍有餘裕，放寬到 50 可讓檔名更好辨識。但這會再次改變命名格式，若要做應與本變更一起做而非日後追加。目前維持 30 不動 —— 本變更的目標是修正碰撞，不是重新設計命名。
