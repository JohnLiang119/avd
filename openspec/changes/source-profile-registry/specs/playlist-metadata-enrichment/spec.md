## Purpose

規範清單項目缺少標題、片長與發布時間時的補齊行為：何時啟動、如何在不延後使用者看到清單的前提下漸進回填，以及面對來源限流與局部失敗時的容忍程度。

## ADDED Requirements

### Requirement: 補齊不得延後使用者看到清單

補齊 MUST 在勾選對話框顯示之後才進行。系統 MUST NOT 為了取得完整資訊而延後對話框的出現。

#### Scenario: 解析一個清單資料不完整的來源

- **WHEN** 使用者解析一個清單資料不完整的來源
- **THEN** 系統在取得項目清單後立即顯示勾選對話框（項目以退化標籤呈現），補齊於其後進行

### Requirement: 補齊結果須漸進回填至已顯示的清單

補齊取得的標題、片長與發布時間 MUST 就地更新到已顯示的勾選對話框上。使用者 MUST NOT 需要關閉再重開對話框才看得到補齊結果，且既有的勾選狀態 MUST 在更新過程中保持不變。

#### Scenario: 補齊過程中的清單更新

- **WHEN** 補齊陸續取得結果
- **THEN** 對話框中對應項目的標題與片長就地更新，使用者已做的勾選不受影響

#### Scenario: 使用者於補齊完成前就開始下載

- **WHEN** 使用者在補齊尚未完成時即確認並開始批次下載
- **THEN** 下載照常進行，尚未補齊的項目不因此失敗，其標題於下載階段自行取得

### Requirement: 補齊為增益而非前提

個別項目補齊失敗 MUST NOT 使該項目無法被選取或下載，亦 MUST NOT 使整體解析被視為失敗。補齊失敗的項目 MUST 保留其退化標籤。

補齊整體失敗或超出其時間預算時，系統 MUST 保留已補齊的結果並讓使用者繼續操作。

#### Scenario: 部分項目補齊失敗

- **WHEN** 補齊過程中部分項目無法取得資訊
- **THEN** 該些項目保留退化標籤，仍可被勾選與下載，其餘項目正常顯示補齊後的資訊

#### Scenario: 補齊超出時間預算

- **WHEN** 補齊耗時超過其預算
- **THEN** 系統停止補齊、保留已取得的結果，使用者可繼續選片與下載

### Requirement: 補齊須對來源限流採退避重試

補齊 MUST 分批進行並於批次之間節流，以降低觸發來源限流的機率。遭遇限流類回應時，系統 MUST 退避後重試，MUST NOT 比照列表階段將其視為永久性失敗而立即放棄。

#### Scenario: 來源以限流回應

- **WHEN** 補齊過程中來源以限流回應（如 HTTP 412／429）
- **THEN** 系統退避後重試該批，而非立即將這些項目標記為無法補齊

#### Scenario: 列表階段的策略不受影響

- **WHEN** 列表階段遭遇 extractor 失敗
- **THEN** 其快速失敗策略維持不變，不因補齊階段採用退避重試而改變

### Requirement: 補齊須可被取消

使用者關閉勾選對話框或取消本次新增時，系統 MUST 停止仍在進行的補齊並終止其背景行程。

#### Scenario: 使用者於補齊進行中關閉對話框

- **WHEN** 使用者在補齊尚未完成時關閉勾選對話框
- **THEN** 補齊立即停止，背景行程被終止，不留下持續佔用網路的作業
