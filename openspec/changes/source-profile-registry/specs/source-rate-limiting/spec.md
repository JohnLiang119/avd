## Purpose

規範來源限流（如 HTTP 429／412）的處置：如何辨識、如何對使用者表達，以及在哪些階段退避重試 —— 使暫時性的「稍後再試」不被呈現為故障，也不被快速失敗策略誤殺。

## ADDED Requirements

### Requirement: 限流須被辨識為暫時性狀況

系統 MUST 能自來源的錯誤回應中辨識出限流類狀況（例如 HTTP 429 Too Many Requests、HTTP 412 Precondition Failed，或語義等同的訊息）。

限流 MUST NOT 被歸類為確定性錯誤 —— 它會隨時間自行解除，與「影片不存在」「私人影片」等永久性失敗性質不同。

#### Scenario: 來源以限流回應

- **WHEN** 解析或補齊收到限流類的錯誤回應
- **THEN** 系統將其判定為暫時性狀況，而非確定性失敗

#### Scenario: 非限流的失敗不受影響

- **WHEN** 解析收到與限流無關的錯誤（例如來源不存在、格式不支援）
- **THEN** 系統維持既有的判定與處置，不因本需求而改變

### Requirement: 限流須以可行動的訊息告知使用者

呈現給使用者的限流訊息 MUST 說明這是暫時性狀況且稍後可再試，MUST NOT 只呈現來源的原始技術訊息而讓使用者誤以為程式故障。

錯誤紀錄中 MUST 保留未經改寫的原始訊息，供事後追查。

#### Scenario: 解析因限流而失敗

- **WHEN** 解析因來源限流而失敗
- **THEN** 使用者看到的訊息表明來源暫時限流、請稍後再試
- **AND** 錯誤紀錄中仍保有來源回傳的原始訊息全文

### Requirement: 限流須退避重試，且此例外橫跨列表與補齊兩階段

遭遇限流時，系統 MUST 退避一段時間後重試，重試次數 MUST 有上限。此行為 MUST 同時適用於清單列表與 metadata 補齊兩個階段。

這是「列表階段快速失敗」原則的**明確例外**：該原則的理由是 extractor 層級的失敗多為永久性，而限流正是反例。此例外 MUST 僅適用於限流類狀況，其餘 extractor 失敗仍維持快速失敗。

重試 MUST 受解析階段既有的總時長上限約束，MUST NOT 因退避而使等待無限延長。

#### Scenario: 列表階段遭遇限流

- **WHEN** 清單列表階段收到限流回應
- **THEN** 系統退避後重試，而非立即放棄

#### Scenario: 補齊階段遭遇限流

- **WHEN** metadata 補齊階段收到限流回應
- **THEN** 系統退避後重試該批

#### Scenario: 重試次數用盡

- **WHEN** 退避重試達到次數上限仍持續被限流
- **THEN** 系統以限流訊息告知使用者，不再繼續重試

#### Scenario: 退避不得突破總時長上限

- **WHEN** 退避重試的累計等待將超過解析階段的總時長上限
- **THEN** 系統停止重試並依既有的逾時行為結束，不使等待無限延長

#### Scenario: 其他 extractor 失敗維持快速失敗

- **WHEN** 列表階段遭遇非限流的 extractor 失敗
- **THEN** 系統維持不重試、迅速回報，行為與本需求引入前相同

### Requirement: 限流的間接徵狀亦須納入辨識

來源的限流未必以明確的 HTTP 狀態碼呈現。當來源以「內容看似缺失」的形式回應被擋的請求，而該回應在實務上與限流無法區分時，系統 MUST 亦將其視為可退避重試的暫時性狀況。

此類徵狀的成因具有歧義（既可能是限流，也可能是內容確實不可取用），故對使用者的訊息 MUST 誠實反映此不確定性，MUST NOT 斷言為單一原因。

#### Scenario: 來源以缺失內容的形式回應被擋的請求

- **WHEN** 解析失敗的訊息屬於已知的限流間接徵狀（例如來源頁面缺少辨識帳號所需的欄位）
- **THEN** 系統退避重試，處置與明確的限流回應相同

#### Scenario: 成因具歧義時的訊息

- **WHEN** 系統因間接徵狀而判定為暫時性狀況並最終仍告失敗
- **THEN** 訊息同時陳述「請求過於頻繁」與「內容可能不可取用」兩種可能，而非斷言其一
- **AND** 錯誤紀錄中仍保有來源回傳的原始訊息全文
